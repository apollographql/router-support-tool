## ❗ BREAKING ❗

- Fix `mode: job` failing to re-collect via `helm upgrade`/`helm install`

  A second `helm upgrade` under `mode: job` always failed with a Kubernetes "field is immutable"
  error, because the Job's fixed name (`router-diagnostics-job`) meant every upgrade tried to
  mutate the same Job's `spec.template`, which Kubernetes does not allow. A second
  `helm install` into the same release name failed outright with "cannot re-use a name
  that is still in use."

  Each collection now gets its own uniquely-named Job, `router-diagnostics-job-{{ .Release.Revision }}`,
  with `helm.sh/resource-policy: keep` so Helm doesn't prune the previous run's Job the
  moment a new one supersedes it.

  **Breaking**: The Job's name is no longer the fixed `router-diagnostics-job`. Anything
  that referenced that name directly needs to use `router-diagnostics-job-<n>` instead.
  Upgrading an existing `mode: job` install to this version also prunes its current Job
  once, during that one upgrade, since the old fixed name predates the `resource-policy:
  keep` annotation. Every upgrade after that is safe. The ServiceAccount/Role/RoleBinding
  name (`router-diagnostics-job`) is unchanged.

- Collect job-mode container memory and CPU from the kubelet with `nodes/stats` only

  Under `mode: job` the chart now runs a `router-resource-usage` script that reads the kubelet
  directly from the Job's pod and keeps only the router's pods, instead of the `nodeMetrics`
  collector which needed `nodes/proxy`. The ClusterRole holds `nodes` (list) and `nodes/stats`.
  When a node's kubelet can't be read, that node has no memory or CPU data and the bundle says
  why. The Job's pod now uses a short-lived projected ServiceAccount token
  (`expirationSeconds: 600`). Bundles from `mode: job` now hold
  one `host-collectors/run-host/router-resource-usage/nodes/<node-name>.json` per node in place of `node-metrics/`,
  and the Job image gains a pinned `python3`. `mode: local` is unchanged.

- Fix `mode: job` collecting no router metrics when the chart is rendered by ArgoCD

  `mode: job` looked up router pod IPs once, when the chart rendered, using Helm's `lookup`.
  `lookup` returns nothing under `helm template`, which is all ArgoCD and similar GitOps tools
  run, so those installs collected no metrics and the bundle didn't say why. Under `helm install`,
  the IPs also went stale as pods were replaced after install.

  The Job now finds the pods matching `selector` each time collection runs and scrapes each one
  directly, the same way `mode: local` already does.

  **Breaking**: `mode: job` metrics move from `router-metrics-<pod-name>/result.json` to
  `host-collectors/run-host/router-metrics/pods/<pod-name>.txt`, the path `mode: local` already
  uses. Each file is now the pod's raw Prometheus text response rather than troubleshoot.sh's
  `http` result JSON.


## 🚀 Features

- Add the router-resource-usage collector script and its unit tests

  Adds a standard-library Python script that lists the router's pods through the API server, reads
  each node's kubelet once, and keeps only those pods. It names the reason for every file it
  doesn't write. Its unit tests run in CI via `mise` by running `mise run test-resource-usage`.

- Add collect.ps1 for Windows support in mode: local

  Windows customers can now run `.\collect.ps1 -Namespace <namespace>` in PowerShell.
  The script downloads and caches the pinned `support-bundle.exe` binary (keyed by version
  and architecture, from the matching `windows_amd64` or `windows_arm64` release asset),
  checks for `kubectl` on PATH, and runs `support-bundle` with the same flags as the shell script.

- Run the collection Job under your own ServiceAccount with `job.serviceAccount.create`

  In `mode: job`, set `job.serviceAccount.create: false` and `job.serviceAccount.name` to the
  name of a ServiceAccount that already exists in the release namespace. The chart then creates
  no ServiceAccount, Role, RoleBinding, ClusterRole or ClusterRoleBinding, so installing it
  needs no RBAC permissions, and the Job runs as the ServiceAccount you named. That
  ServiceAccount must hold the grants listed in the specs, which are the ones the chart would
  otherwise create. Without them, the collection reports what it could not read.

  Nothing changes if you leave the values unset.

- Publish collect.ps1 as a GitHub Release asset

  `collect.ps1` is now attached to each GitHub Release alongside `collect.sh`.


## 🐛 Fixes

- Fix the Job image build failing on the stale ca-certificates pin

  Alpine 3.24 replaced `ca-certificates` `20260909-r0` with `20261020-r0` and no longer
  serves the old version, so `apk add` in the Job image's Dockerfile failed with
  `breaks: world[ca-certificates=20260909-r0]` and the image could not be built. The pin
  is bumped to `20261020-r0`.

  To keep this from recurring, Renovate now proposes the Job image's apk pins (the
  repology-sourced `aws-cli`, `curl` and `ca-certificates` versions) with no release-age
  wait, and groups them into one PR. Alpine drops a package's previous version as soon as
  a new one lands, so a delayed bump leaves the exact pin unresolvable, and separate PRs
  for packages Alpine updates together would each fail the image build on the other
  packages' stale pins.

- Fix the Job image build failing on the stale curl pin

  Alpine 3.24 replaced `curl` `8.22.0-r0` with `8.23.0-r0` and no longer serves the old
  version, so `apk add` in the Job image's Dockerfile fails with
  `breaks: world[curl=8.22.0-r0]` on any build that misses the Docker layer cache. The pin
  is bumped to `8.23.0-r0`.

- Fix `mode: job` GCS uploads failing with "no active account selected"

  `job.storage.provider=gcs` with a key-file-based credential (`existingSecret` or a
  static `credentialsJson`) always failed the upload step with `ERROR:
  (gcloud.storage.cp) You do not currently have an active account selected.`
  `GOOGLE_APPLICATION_CREDENTIALS` satisfies Application Default Credentials for client
  libraries, but the `gcloud` CLI binary itself still needs an explicitly activated
  account - nothing in `collect-and-upload.sh` ever did that. Confirmed against a real
  GCS bucket: collection always succeeded, but the upload never did.

  `collect-and-upload.sh`'s `gcs` branch now sets `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`
  to `$GOOGLE_APPLICATION_CREDENTIALS` before the upload, only when that env var is set.

- Redact router.yaml secrets in the `last-applied-configuration` annotation

  A ConfigMap created with `kubectl apply` carries a second copy of `router.yaml` in its
  `kubectl.kubernetes.io/last-applied-configuration` annotation and is collected in
  `cluster-resources/configmaps/*.json`. That copy is a JSON string inside a JSON string, so its
  quotes and newlines are escaped twice, and the redactors for JWKS fetch headers, header
  `insert`/`propagate` values and defaults, Redis `username`/`password` and the subgraph URL
  override only allowed for one level of escaping. They masked the data copy and left the
  annotation copy unredacted. The patterns now accept any number of backslashes.

- Redact a quoted response cache `shared_key` in the `last-applied-configuration` annotation

  A quoted `shared_key` was masked in the collected `router.yaml` but not in the
  `kubectl.kubernetes.io/last-applied-configuration` annotation that `kubectl apply` stores on a
  ConfigMap, which lands in `cluster-resources/configmaps/*.json`. The annotation holds the
  `router.yaml` string inside a JSON string inside the file so the quotes around the value are
  escaped twice and the redactor only allowed for one level. It now accepts any number of
  backslashes before the quote.

- Fix `mode: local` metrics collection for users who rely on the default kubeconfig.

  The `router-metrics` script runs with a stripped environment that keeps `KUBECONFIG` but drops
  HOME`. Therefore, a `kubectl` using the default `~/.kube/config` found no kubeconfig and the
  bundle said it could not list pods. `collect.sh` and `collect.ps1` now set `KUBECONFIG` to
  the default kubeconfig when the user hasn't set it.

- Redact the response cache invalidation shared key

  `response_cache.subgraph.*.invalidation.shared_key` is the key a caller must present to
  the router's cache invalidation endpoint so anyone holding it can purge cached
  responses. None of the existing redactors matched it. Therefore, a literal value in
  `router.yaml` was collected into the bundle unmasked. A new redactor masks it in the
  collected `router.yaml` and in the `last-applied-configuration` annotation, whether the value is
  unquoted or quoted. An empty `shared_key: ""` is left alone.


## 🛠 Maintenance

- Test against the Router 3 preview

  The collect script integration tests now install the official router chart at
  `3.0.0-preview.0` in a separate job and the RTF test plan adds a
  `v3.0.0-preview.0` variant with full redaction and Router 3 fixtures.

- Add documentation for running `mode: local` on Windows.

- Add Windows CI logic test for collect.ps1 (mocked support-bundle)

  A new GitHub Actions job (`exercise_local_collect_windows`) runs `collect.ps1`
  on `windows-latest`, exercising its argument parsing, cache management, binary
  invocation, and exit-code passthrough. `collect.ps1` gains a
  `SUPPORT_BUNDLE_BIN_OVERRIDE` env var: when set, it replaces the computed
  versioned `.exe` path so tests can point `& $Bin` at a PowerShell stub instead.

- Check the documented memory and CPU signals are in the bundle

  The bundle checks now read the signals listed in the spec's "Memory and CPU
  information collected" table and fail if the bundle lacks one.

- Correct the minimum router version for the jemalloc metrics to v2.5.0

  The specs and docs said the router serves the jemalloc memory gauges from v2.16.3. The
  router's changelog shows they were added in v2.5.0.

- Correct the memory and CPU claims in the specs and docs

  The router's Prometheus endpoint does not serve `process_resident_memory_bytes` or
  `process_cpu_seconds_total`. It serves only jemalloc memory gauges and only on builds with
  jemalloc. The specs and docs no longer list those two signals. Container RSS and CPU come
  from the kubelet Summary API through the `nodeMetrics` collector, which needs `nodes`,
  `nodes/proxy` and `nodes/stats`. `job.collectNodeMetrics: false` now says plainly what is
  lost.

- Document the kubelet stats collection in mode: job

  Under `mode: job`, container memory and CPU now come from the kubelet and need only `nodes/stats`
  and `nodes`, not `nodes/proxy`. The docs describe the two grants, where the stats land in the
  bundle, and the lines that say why stats are missing. The `mode: local` page now covers the
  grants that mode needs.

- Document how metrics are found at collection time and what to do when they're missing

  The Collecting Metrics page and the `mode: job` and `mode: local` references now describe
  how router metrics are collected after the move to finding pods when collection runs.

- Document how mode: job behaves under ArgoCD.

- Document running the Job under your own ServiceAccount.

- Document supported router versions and the response cache redaction

  The overview and getting-started pages now state that the tool supports Router 2.4.0
  through the 3.0.0 preview. The redaction descriptions now include the response cache's
  invalidation `shared_key`, its Redis config and the OTLP gRPC TLS key, and the Data
  Collected page notes that a key set through an environment variable, or left empty,
  isn't masked in `router.yaml`.

- Specify running `mode: job` under your own ServiceAccount

  The specs now describe `job.serviceAccount.create` and `job.serviceAccount.name`. With
  `create: false` and a `name`, the collection Job runs as a ServiceAccount you already own
  and the chart creates no RBAC objects.

- Specify least-privilege container memory and CPU collection for job mode

- Run the Router 2 full-redaction RTF variant on v2.19.0, including the response cache connector

  Router 2.19.0 adds `response_cache.connector`, which earlier versions reject. The Router 2 `full`
  redaction fixtures now carry a connector block, so the RTF test plan runs them on `v2.19.0` and
  moves `v2.17.0` to the base config like the other earlier 2.x versions. The connector block has
  an invalidation `shared_key` (unquoted on `all`, quoted on a source) and Redis credentials as a
  URL-embedded password on `all` and as separate username and password fields on a source.

- Run the job-mode kubelet stats checks in RTF

- Check in RTF that missing kubelet stats come with a stated reason

  The job-mode kubelet stats collector must say why it collected nothing. RTF now checks three cases:

  - No pod matches the selector.
  - Collection is declined at install, in a new `kubelet-declined` condition that installs the chart
    with `job.collectNodeMetrics: false`.
  - The kubelet refuses the Job's token because its ServiceAccount lacks `nodes/stats`, in one variant
    (`healthy` on the newest Router 2).

- Test every shape of the response_cache shared_key redactor and sweep the whole bundle for it

  A new `test-shared-key-redactor` check runs the redactor's patterns, read from the rendered
  chart, over the shapes the key can take: unquoted, quoted (plain and JSON-escaped), flow
  style, JSON, the `last-applied-configuration` annotation, and the empty and bare forms that
  must be left alone. The RTF scenario also now searches the entire extracted bundle for the
  shared key sentinels instead of only the dedicated ConfigMap file.

- Search the whole RTF bundle for every redaction sentinel

  The `full` redaction RTF variants now search every file in the extracted bundle for each
  `SENTINEL_*` secret the variant's ConfigMap fixture plants, instead of checking the dedicated
  `configMap` collector's file alone. `router.yaml` is also collected in
  `cluster-resources/configmaps/*.json` and, for a ConfigMap created with `kubectl apply`, in its
  `last-applied-configuration` annotation, where it is escaped twice. A failure lists each
  leaked sentinel with every file it was found in.
