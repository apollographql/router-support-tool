# Deployment — v1 (on-demand collection)

This file covers the `router-diagnostics` chart and the deployment tiers that use it. For the step-by-step customer-facing setup flow, see `specs/user_experience.md`. This file is the technical reference for that flow — deployment tiers, RBAC, and cluster footprint. Apollo Operator deployment is specified in `specs/deployment/v1/operator.md`.

v1 deploys on-demand (flare-style) support bundle collection for Kubernetes deployments only.

## Deployment tiers
The table below outlines the types of deployments supported by the tool and what information the customer needs to provide for each.

| Deployment tier | Customer supplies | How the tool locates the router |
| --- | --- | --- |
| **Apollo Operator** | Nothing | See `specs/deployment/v1/operator.md` |
| **Official Apollo router Helm chart** | `namespace` | Standard chart label `app.kubernetes.io/name=router`. ConfigMap name, config key, and ports are fixed by the chart |
| **Raw manifests / custom deployment** | `namespace`, `selector`, `configMapName` | Entirely from customer-supplied values — no convention applies |

## Collection modes

Every non-Operator deployment runs collection in one of two modes, set via the chart's `mode` value:

- **`mode: local`** — you run the collection yourself, with your own kubectl access.
- **`mode: job`** — a Kubernetes Job runs the collection in-cluster, for teams whose kubectl access to production is restricted and who need a platform team to run it on their behalf.

See [Helm chart](#helm-chart) below for how the two modes render differently.

## Prerequisite: the collection binary

In order to use the support tool, troubleshoot's `support-bundle` binary must be provided. The table below outlines who is responsible for supplying it.

| Path | Who supplies the binary | Customer prerequisite |
| --- | --- | --- |
| `mode: local` | The invoking user's machine | Install the plugin (see below) |
| `mode: job` | The Job's container image | None — the image ships the binary |

`mode: job` requires an image containing the binary. Apollo owns and publishes that image. For local mode, the customer installs the plugin once, either as a kubectl plugin via krew:

```bash
kubectl krew install support-bundle
```

or as a standalone binary, for CI or for machines without `krew`:

```bash
curl -L https://github.com/replicatedhq/troubleshoot/releases/latest/download/support-bundle_linux_amd64.tar.gz | tar xzvf -
```

### troubleshoot.sh support-bundle version

The two paths differ in who controls the troubleshoot.sh support-bundle version:

| Path | support-bundle version | Controlled by |
| --- | --- | --- |
| `mode: job` | Pinned by the image tag | Apollo |
| `mode: local`, Operator | Whatever plugin the user installed — `krew` installs latest | The customer |

## Helm chart

Non-Operator customers install a single Helm chart, `router-diagnostics`, with a required `mode` value. Rather than building separate mechanisms for local invocation and for restricted-access clusters, one chart serves both:

- **`mode: local`** — renders only the spec, as a cluster ConfigMap. The customer runs the collection themselves with their own kubectl credentials.
- **`mode: job`** — renders the same spec ConfigMap **plus** a Job and its ServiceAccount/RBAC, which runs the collection in-cluster. For customers whose kubectl access to production is restricted and who need a platform team to run it on their behalf.

Both modes render the spec as a ConfigMap labelled for `--load-cluster-specs` to discover. Both use the same spec and the same collection engine. Only who runs it, where, and how the bundle is retrieved differ.

```
router-diagnostics/
├── templates/
│   ├── spec-configmap.yaml     # always rendered
│   ├── job.yaml                # rendered only if mode: job
│   └── job-rbac.yaml           # rendered only if mode: job
└── values.yaml
```

```yaml
# templates/spec-configmap.yaml — always rendered
apiVersion: v1
kind: ConfigMap
metadata:
  name: router-diagnostics-spec
  labels:
    troubleshoot.sh/kind: support-bundle
data:
  support-bundle-spec: |
    {{ include "router-diagnostics.spec" . }}
  redactor-spec: |
    {{ include "router-diagnostics.redactors" . }}
```

```yaml
# templates/job.yaml — only rendered if mode: job
{{- if eq .Values.mode "job" }}
apiVersion: batch/v1
kind: Job
...
{{- end }}
```

### Chart values

This table is the complete `values.yaml` interface.

| Value | Required | Default | Applies to | Purpose |
| --- | --- | --- | --- | --- |
| `namespace` | Yes | — | All non-Operator tiers | The router's namespace. Rendered into every collector that accepts it, including `clusterResources.namespaces` as a single-element list. Never rely on the kubectl context fallback. |
| `mode` | Yes | — | All non-Operator tiers | `local` or `job` |
| `selector` | Raw-manifest tier only | The official chart's `app.kubernetes.io/name=router` label | Raw manifests / custom | Pod label selector, e.g. `app=my-router` |
| `configMapName` | Raw-manifest tier only | Label-based targeting, no name needed | Raw manifests / custom | Name of the ConfigMap holding the router config |
| `job.podAnnotations` | No | `{sidecar.istio.io/inject: "false", linkerd.io/inject: disabled}` | `mode: job` only | Annotations merged onto the Job's pod template, customer values win over the defaults — see [Service mesh environments](#service-mesh-environments-mode-job) |
| `job.podLabels` | No | `{}` | `mode: job` only | Arbitrary labels merged onto the Job's pod template — see [Service mesh environments](#service-mesh-environments-mode-job) |
| `logs.maxAge` | No | Unset — no age cap | All tiers | Maps to the `logs` collector's `limits.maxAge`. How far back to reach, e.g. `2h` |
| `logs.maxLines` | No | `10000` (troubleshoot.sh default) | All tiers | Maps to `limits.maxLines`. Lines from newest per container |

## Chart Invocation

**Official Apollo Helm chart, `mode: local`:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace <namespace> \
  --set namespace=<router_namespace> \
  --set mode=local

kubectl support-bundle --load-cluster-specs
```

**Raw-manifest / custom deployment, `mode: local`:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace <namespace> \
  --set namespace=<router_namespace> \
  --set selector="app=my-router" \
  --set configMapName=my-config \
  --set mode=local

kubectl support-bundle --load-cluster-specs
```

**`mode: job`** — a platform team member with cluster access installs the chart with `mode=job` (plus `selector`/`configMapName` if the deployment is raw-manifest). The Job runs the collection using its namespace-scoped ServiceAccount, and the platform team retrieves the bundle. See `specs/storage` for details on retrieving the bundle.

**Apollo Operator** — See `specs/deployment/v1/operator.md`

### Service mesh environments (`mode: job`)

This applies to `mode: job` only because it is the only mode where the chart creates a pod.

**Injecting a sidecar risks the Job never completing.** A Job's pod is expected to terminate when its work finishes, and Kubernetes only marks a Job `Complete` once every container in its pod has exited. An injected mesh proxy (e.g. `istio-proxy`) is a long-running sidecar that keeps waiting for traffic after the collection container is done,therefore, the pod sits in `Running` indefinitely instead of reaching `Completed`. That leaves a stuck workload in the customer's production namespace and no clean signal that collection succeeded. For a diagnostic tool whose central promise is that it is safe to run against a production router, leaving debris behind is the worse outcome.

Given that, the chart sets `job.podAnnotations` to disable injection by default, but only for the two meshes the chart can concretely name, Istio and Linkerd. This is a best-effort default, not a claim to cover every mesh, and it is a starting point the customer can override.

- **A different mesh** — the customer adds their mesh's own opt-out annotation via `job.podAnnotations`. Helm merges customer-supplied keys over the chart's defaults, so this is additive.
- **Policy requires every pod to stay in the mesh** — the customer overrides the specific default key back, e.g.:

  ```yaml
  job:
    podAnnotations:
      sidecar.istio.io/inject: "true"
  ```

  That is a property of the customer's own environment and policy, not something this chart can resolve on their behalf. **This is safe from the stuck-`Completed` risk only if the mesh's sidecar is a Kubernetes-native sidecar** (`restartPolicy: Always` init container, GA in Kubernetes 1.29+; supported by recent Istio and Linkerd releases) — the kubelet then terminates the sidecar once the main container exits, so the Job still completes with the proxy injected. On a cluster/mesh combination that predates native sidecar support, overriding the default reintroduces the stuck-Job risk the default exists to avoid.

The chart records whether it disabled injection in `meta.json`'s `sidecar_injection_disabled` field, see `specs/collection/meta_json.md` → Render-time facts. That rules out one specific cause of an empty metrics section — interception via the Job's own mesh membership — but does not on its own confirm a mesh issue exists or attribute the section fully. Disambiguating a mesh-blocked scrape from a disabled or misconfigured exporter still requires reading the collected `router.yaml` alongside it, see `specs/collection/base_spec.md` → Service mesh and proxy environments.


#### Running outside the mesh doesn't have to mean losing metrics

In this case the metrics port needs an explicit exception. `logs`, `clusterResources`, `nodeMetrics`, `configMap` all reach their data through the Kubernetes API server or the kubelet, which the mesh does not sit in front of, so an un-injected pod doesn't affect them. The Prometheus scrape is the one collector that talks directly to a router port, and a mesh enforcing strict mTLS will reject it from a pod outside the mesh.

The fix is on the router's side, not the Job's: the customer configures their mesh to exempt the router's metrics port from mTLS enforcement — Istio's `PeerAuthentication` set to `PERMISSIVE` scoped to that port (or `traffic.sidecar.istio.io/excludeInboundPorts` on the router pod), Linkerd's `config.linkerd.io/skip-inbound-ports` annotation on the router pod. This is a narrow, standard exception — it affects only the one metrics port on the router's own pod, not mTLS anywhere else — and is the same mechanism many clusters already use so an external, non-mesh Prometheus can scrape mesh-enrolled workloads. Because it changes the router's deployment rather than the Job's, it's outside `job.podAnnotations`; it's guidance for the customer's platform team to apply once, not something this chart sets.

This applies to `mode: local` too — it also runs outside the mesh — so it's worth documenting once, for both modes, rather than as a `mode: job`-specific gap. If a platform team won't grant even this scoped exception, the gap is real: the only in-mesh route to that data is an `exec`-based scrape from inside the router's own pod, and `exec` collectors are deliberately excluded from the base spec (see `specs/architecture.md` → the base spec runs entirely against the API server, the kubelet, and external endpoints) — closing that gap means a future, heavier spec, not a v1 fix.

## Cluster footprint

| Path | Standing footprint |
| --- | --- |
| Apollo Operator | The Operator-provisioned spec ConfigMap |
| `mode: local` | Spec ConfigMap + Helm release metadata |
| `mode: job` | Spec ConfigMap + Helm release metadata + ServiceAccount/Role/RoleBinding. The Job itself is transient |

Installing the chart creates a persistent object in a production cluster. The tradeoff runs the other way once installed: subsequent collections are just `kubectl support-bundle --load-cluster-specs`, with no reinstall. Customers who want nothing left behind can `helm uninstall` after collecting.

## Permissions

**`mode: local`** requires only permission to create a ConfigMap in the target namespace.

**`mode: job`** additionally requires creating a Job, a namespace-scoped ServiceAccount, a Role/RoleBinding, and a ClusterRole/ClusterRoleBinding (for `nodeMetrics`'s cluster-scoped grants).

**Running the collection** requires read access to the router's namespace in both modes, sourced differently:

| | `mode: local` | `mode: job` |
| --- | --- | --- |
| Identity | The invoking user's existing kubectl credentials | A namespace-scoped ServiceAccount created by the chart |
| Who runs it | The customer | A platform team member, via the Job |

#### `nodeMetrics` RBAC

`nodeMetrics` needs three separate grants to reach `/api/v1/nodes/<node>/proxy/stats/summary`:

- **`nodes` (list)** — to resolve node names when neither `nodeNames` nor `selector` is set.
- **`nodes/proxy` (get)** — required unconditionally by the API server for any request matching the `/nodes/{name}/proxy/{path}` URL pattern. This is a broad grant: Kubernetes' own RBAC good-practices documentation states it "provides access to privileged kubelet APIs that can retrieve container logs or execute and attach to pod processes... bypasses audit logging and admission control," and is explicitly "not a read-only permission." What this tool does with it is read-only, but the grant itself authorizes more than that one use, and it cannot be scoped to just the router's nodes.
- **`nodes/stats` (get)** — required separately by the kubelet's own authorization check, layered on top of `nodes/proxy`, not a substitute for it.

Declining `nodes/proxy`/`nodes/stats` still leaves `nodes` access (node pressure conditions) and everything `clusterResources` provides — OOM kill occurrences and last state, restart counts, configured limits. What's lost is container memory/CPU trajectory over time — but `nodeMetrics` is a fallback for that signal, not the preferred path: enabling the Prometheus exporter gets the same container-level usage-over-time signal without any of these grants, so customers should be pointed toward Prometheus first. See `specs/collection/base_spec.md` → `nodeMetrics` is a fallback, not the preferred path.

See `specs/collection/base_spec.md` for the rest of the permission set the collectors need.
