# Deployment — v1 (on-demand collection)

v1 deploys **on-demand (flare-style) collection only**. Scheduled and threshold-triggered collection, and the standing workloads they require, are v2 — see `specs/trigger/`.

This spec answers, for v1: which deployment tiers are supported, what each tier requires from the customer, where collection executes, what footprint it leaves in the cluster, and what permissions it needs.

v1 is **Kubernetes-only**. ECS, Fargate, and standalone VM deployments are out of scope. All data stays in customer infrastructure; nothing is sent to Apollo.

**Scope:** this file covers the `router-diagnostics` chart and the deployment tiers that use it. **Apollo Operator deployment is specified in `specs/deployment/v1/operator.md`** and is referenced here only where a comparison across tiers requires it — the tier table, the prerequisite and footprint tables, and the engine-version asymmetry. Anything specific to how the Operator provisions, configures, or gates the spec belongs in that file, not this one.

---

## The constraint that shapes everything here

`kubectl support-bundle` takes [spec *sources*](https://troubleshoot.sh/docs/support-bundle/collecting) — a file, URL, OCI artifact, or Kubernetes Secret/ConfigMap — **not collector parameters.** Customer-specific values (namespace, pod selector, ConfigMap name, redaction preferences) must therefore live *inside the spec YAML itself*. There is no invocation-time flag that can supply them: the one flag that accepts arbitrary key-values, `--metadata`, only attaches bundle-labelling metadata (it lands at `metadata/user.json`) and does not feed collectors.

Every deployment decision below follows from this. A customer-specific value reaches a collector only by being templated into the rendered spec, which is what makes a values-driven Helm chart the delivery mechanism rather than a published static spec plus CLI flags.

---

## One spec, populated three ways

**v1 ships exactly one spec.** There is a single base spec definition, authored once, and it is the only collection artifact v1 produces. What differs across deployment tiers is *who fills in its targeting values* — the Operator, or the chart from customer-supplied values — not which spec runs.

This is deliberate and worth stating plainly, because an earlier design did ship two specs (a self-contained Operator variant and a parameterized variant for everyone else) and that approach is rejected: two artifacts describing the same collection will drift, and a drifted spec means Operator and non-Operator customers silently send support different bundles from the same tool version. Any change to what is collected must land in one place. If a tier's needs ever cannot be met by populating the one spec's values, that is a signal to revisit the targeting parameters rather than to fork the spec.

## Deployment tiers

| Deployment tier | Support in v1 | Customer supplies | How the tool locates the router |
| --- | --- | --- | --- |
| **Apollo Operator** | Full support, zero config | Nothing | The Operator populates the spec's targeting values from conventions it already knows — see `specs/deployment/v1/operator.md` |
| **Official Apollo router Helm chart** | Full support | `namespace` | Standard chart label `app.kubernetes.io/name=router`; ConfigMap name, config key, and ports are fixed by the chart |
| **Raw manifests / custom deployment** | Supported | `namespace`, `selector`, `configMapName` | Entirely from customer-supplied values — no convention applies |

`namespace` is required at every non-Operator tier and cannot be eliminated, and it must be templated into **every** collector that accepts it — not only the ones that obviously need targeting. The field name differs by collector, and so does the consequence of omitting it:

| Collector | Field | If omitted |
| --- | --- | --- |
| `logs`, `configMap` | `namespace` (string) | Falls back to the invoking kubectl context's namespace. If that context is not pointed at the router, the collector silently searches the wrong place and returns empty. |
| `clusterResources` | **`namespaces` (list)** | Falls back to **every namespace in the cluster.** |

Both failure modes are silent, and they fail in opposite directions — which is why this is called out rather than left to whoever writes the YAML.

**The `clusterResources` case is the more serious of the two and the easier to miss**, because the field is named differently (`namespaces`, plural, taking a list) and because omitting it produces *more* data rather than less, so nothing about the resulting bundle looks broken. Confirmed from the collector source: with no `namespaces` set and no namespace otherwise supplied, it enumerates all namespaces and collects from each. Since `clusterResources` gathers ConfigMaps with their full `data`, an unscoped run puts every ConfigMap in the cluster — unrelated teams' application config included — into a bundle the customer may hand to Apollo.

A namespace-scoped ServiceAccount would make the cluster-wide listing fail, but that is not a safeguard to rely on: `mode: local` commonly runs as an identity with broad read access, in which case the wider collection succeeds quietly. The chart must render `namespaces: [<namespace>]` — the required singular value as a single-element list — and this is worth a regression check in the test matrix: run collection as a cluster-admin identity and assert the bundle contains nothing from outside the router's namespace.

### What the official Apollo Helm chart makes inferable

Confirmed by rendering `oci://ghcr.io/apollographql/helm-charts/router` (tested at v2.10.5) with `helm template`. These are the conventions the chart tier relies on:

| Information | Finding |
| --- | --- |
| ConfigMap name | Exactly the Helm release name (release `my-router` → ConfigMap `my-router`) — no templated suffix or hash |
| Config key in the ConfigMap | `configuration.yaml` |
| Mount path in the container | `/app/configuration.yaml` |
| Standard labels | `app.kubernetes.io/name=router` on every chart resource, including the ConfigMap |
| Health check port | `8088`, paths `/health?live` and `/health?ready` |
| App traffic port | Container `4000`, exposed on the Service as port `80` |
| `APOLLO_GRAPH_REF` / `APOLLO_KEY` | Plain env vars on the container; `APOLLO_KEY` is sourced from a **separate Secret** (`managedFederationApiKey`), structurally separated from the config ConfigMap — a ConfigMap-only read cannot expose it |
| Deployment-type signal | `APOLLO_ROUTER_OFFICIAL_HELM_CHART=true` is set as an env var — the same variable `fleet_detector.rs` checks (`OFFICIAL_HELM_CHART_VAR`) to report `deployment_type=official_helm_chart` |

Metrics values are **not** exposed by default; they appear when `serviceMonitor.enabled=true`, which confirms Prometheus is opt-in at the chart level as well as in `router.yaml`:

| Information | Finding |
| --- | --- |
| Metrics container port | `9090` (matches the `containerPorts.metrics: 9090` default) |
| Metrics Service port | `9090`, `targetPort: metrics` |
| Path | `/metrics` (confirmed via the Deployment annotation `prometheus.io/path: /metrics`) |
| ServiceMonitor | Rendered only when `serviceMonitor.enabled: true`; targets `port: metrics` |
| What actually turns metrics on | `router.configuration.telemetry.exporters.metrics.prometheus.enabled: true` **and** `.listen` inside the router config values — not `serviceMonitor.enabled` alone |

The label-based targeting is the load-bearing finding: because the chart applies `app.kubernetes.io/name=router` to every resource, collectors can target by label rather than by release name, which is why this tier needs only `namespace`.

## Prerequisite: the collection binary

**Installing the chart is not sufficient to collect a bundle.** The chart's only job is to get a populated spec into the cluster; it does not deliver the thing that runs it. troubleshoot.sh is explicit that collection is client-side — *"This does not deploy anything to the cluster, it's all client-side code"* — so something must supply the `support-bundle` binary, and which side that is depends on the path:

| Path | Who supplies the binary | Customer prerequisite |
| --- | --- | --- |
| Apollo Operator | The invoking user's machine | Install the plugin |
| `mode: local` | The invoking user's machine | Install the plugin |
| `mode: job` | The Job's container image | None — the image ships the binary |

For the two local paths, the customer installs it once, either as a kubectl plugin via krew:

```bash
kubectl krew install support-bundle
```

or as a standalone binary, for CI or for machines without `krew`:

```bash
curl -L https://github.com/replicatedhq/troubleshoot/releases/latest/download/support-bundle_linux_amd64.tar.gz | tar xzvf -
```

Installing the plugin puts a single binary in the user's path and deploys nothing to the cluster. `kubectl support-bundle` *is* that binary — this is a genuine second prerequisite alongside the chart, not an implementation detail, and it is the step most likely to be missed because the chart install appears to complete the setup.

Because collection is client-side, `mode: job` requires an image containing the binary. Apollo owns and publishes that image (see `specs/architecture.md`).

### Collection engine version

The two paths differ in who controls the engine version, and this is a real asymmetry rather than a packaging detail:

| Path | Engine version | Controlled by |
| --- | --- | --- |
| `mode: job` | Pinned by the image tag | Apollo |
| `mode: local`, Operator | Whatever plugin the user installed — `krew` installs latest | The customer |

**The plugin version cannot be pinned by us.** It lives on the customer's machine, outside every artifact we deliver, and `krew` tracks latest. There is no mechanism to force a version, and the spec should not pretend otherwise.

That is acceptable because the exposure is a function of *what the spec uses*, not of plugin drift in the abstract. The base spec uses only long-established collectors — `logs`, `clusterResources`, `containerMetrics`, `http`, `configMap`, `helm`. The risk materializes only when the spec adopts a newer collector or field. Hence the rule:

**Adopting a collector or field that raises the minimum supported troubleshoot.sh version is a deliberate, reviewed spec change, called out as such in the PR.** This converts an ambient compatibility risk into a change-control step, which is where it belongs.

Four supporting requirements:

1. **A tested floor.** The spec declares a minimum supported troubleshoot.sh version, and that number comes from a verified run in the test matrix — not from a guess. **Open:** the floor is not yet determined; it should be set when the base spec is first validated against the REP matrix.
2. **Test the floor and a current release.** Drift cuts both ways. A plugin *newer* than anything we tested can change behavior or default redaction, and that direction is unbounded because krew moves on its own schedule.
3. **The engine already records its own version — read it, don't duplicate it.** Nothing enforces a minimum client-side (the plugin will not check a version field we put in the spec), so the mitigation is diagnostic rather than preventive: when a bundle comes back short, support needs to see which engine produced it. That is already available. Every bundle contains **`version.yaml`**, written by troubleshoot.sh with the version that produced it. What the spec must supply is the other half of the comparison — the declared floor, carried as `min_troubleshoot_version` in `meta.json`. See `specs/collection/meta_json.md`.
4. **Offer a pinned download.** krew is the easy path and tracks latest; the standalone binary is the reproducible path, because the release URL can name a specific tag instead of `latest`. Customers in CI or under strict change control should be pointed at a pinned tag.

**Open:** what an older plugin does with an unrecognized field — hard error or silent ignore. A hard error is tolerable, since the customer sees it immediately. A silent ignore is the damaging case: the bundle comes back quietly incomplete and nobody knows to look. This should be verified rather than assumed, because it determines how loud this whole class of problem is.

A consequence worth stating: **`mode: job` is the more reproducible path**, since Apollo pins the engine. That is a reason to prefer the Job in our own test matrix and when a support engagement needs a known-good collection — not a reason to make it the only mode. See [Rejected alternatives](#rejected-alternatives).

### Verified against the troubleshoot.sh docs

Two mechanics this deployment story depends on, confirmed rather than assumed:

- **Bare `--load-cluster-specs` is valid.** It runs with no positional spec argument, collecting only from specs discovered in the cluster. Every invocation in this spec relies on that.
- **Discovery is by label** — a ConfigMap or Secret must carry `troubleshoot.sh/kind: support-bundle`, which is the label the chart's spec ConfigMap sets.

## One chart, two modes

Non-Operator customers install a single Helm chart, `router-diagnostics`, with a required `mode` value. Rather than building separate mechanisms for local invocation and for restricted-access clusters, one chart serves both:

- **`mode: local`** — renders only the spec, as a cluster ConfigMap. The customer runs the collection themselves with their own kubectl credentials.
- **`mode: job`** — renders the same spec ConfigMap **plus** a Job and its ServiceAccount/RBAC, which runs the collection in-cluster. For customers whose kubectl access to production is restricted and who need a platform team to run it on their behalf.

Both modes render the spec as a ConfigMap labelled for `--load-cluster-specs` to discover. Both use the same spec and the same collection engine; only who runs it, where, and how the bundle is retrieved differ.

```
router-diagnostics/
├── templates/
│   ├── spec-configmap.yaml     # always rendered
│   ├── job.yaml                # rendered only if mode: job
│   └── job-rbac.yaml           # rendered only if mode: job
└── values.yaml
```

```yaml
# templates/spec-configmap.yaml — always rendered
apiVersion: v1
kind: ConfigMap
metadata:
  name: router-diagnostics-spec
  labels:
    troubleshoot.sh/kind: support-bundle
data:
  spec.yaml: |
    {{ include "router-diagnostics.spec" . }}
```

```yaml
# templates/job.yaml — only rendered if mode: job
{{- if eq .Values.mode "job" }}
apiVersion: batch/v1
kind: Job
...
{{- end }}
```

### Chart values

Values are grouped by concern — targeting, mode, and redaction read as distinct groups rather than a flat list:

| Value | Required | Applies to | Purpose |
| --- | --- | --- | --- |
| `namespace` | Yes | All non-Operator tiers | The router's namespace. Never rely on the kubectl context fallback. |
| `mode` | Yes | All non-Operator tiers | `local` or `job` |
| `selector` | Raw-manifest tier only | Raw manifests / custom | Pod label selector, e.g. `app=my-router` |
| `configMapName` | Raw-manifest tier only | Raw manifests / custom | Name of the ConfigMap holding the router config |
| `redaction.includeSchema` | No (default `true`) | All non-Operator tiers | Include graph schema/SDL in the bundle; set `false` to strip it entirely |
| `job.sidecarInjection` | No (default `false`) | `mode: job` only | Whether the Job pod joins a service mesh. Defaults to disabled so the Job reliably reaches `Completed`; see [Service mesh environments](#service-mesh-environments-mode-job) |

Every value here reaches only tiers that install the chart. **Operator customers have no chart and therefore no access to any of them** — including `redaction.includeSchema`. How they express the same preferences is specified in `specs/deployment/v1/operator.md`.

`redaction.includeSchema` is nested rather than top-level deliberately. It is the only customer-configurable redactor today, and grouping keeps room for future ones without cluttering the chart's top-level values. Everything else — built-in credential/token redactors and Apollo's custom JWT, auth-config, header-value, operation-body, and subgraph-URL redactors — is fixed with no configuration. See `specs/collection/data_sanitization/`.

Collection-behavior values that are not targeting values (for example opting into previous-container logs) belong to the collection layer and are documented with the base spec.

**There is deliberately no `redisUri` value, and this is settled rather than pending.** The `redis` collector is not in the v1 base spec; see `specs/collection/base_spec.md` → Redis health: not collected in v1 for the full reasoning. The part that belongs to this layer is why no chart value could fix it:

Every value here is templated into the spec ConfigMap, and **that ConfigMap is collected into the bundle** — `clusterResources` gathers ConfigMaps with their full `data`. Since the collector requires its URI inline and a Redis URI commonly embeds credentials, a `redisUri` value would ship a live credential inside the artifact the customer sends to support, protected only by a redaction rule. A Secret-backed value does not help: Helm would read the Secret and template the literal in anyway, and the collector accepts no Secret reference for the URI itself (its `tls.secret` support covers certificate material only).

**The general rule this establishes: a chart value must never carry a credential.** Anything templated into the spec ConfigMap should be assumed to reach the bundle, so targeting values must be things like namespaces, labels, and object names — never secrets.

### Invocation by tier

**Official Apollo Helm chart, `mode: local`:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace production \
  --set namespace=production \
  --set mode=local

kubectl support-bundle --load-cluster-specs
```

**Raw-manifest / custom deployment, `mode: local`:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace production \
  --set namespace=production \
  --set selector="app=my-router" \
  --set configMapName=my-config \
  --set mode=local

kubectl support-bundle --load-cluster-specs
```

**Restricted-access cluster, `mode: job`** — a platform team member with cluster access installs the chart with `mode=job` (plus `selector`/`configMapName` if the deployment is raw-manifest). The Job runs the collection using its namespace-scoped ServiceAccount, and the platform team retrieves the bundle.

**Apollo Operator** — no chart. The Operator writes the same base spec into a cluster ConfigMap, with its targeting values already populated from conventions it knows, and the customer runs:

```bash
kubectl support-bundle --load-cluster-specs
```

That is the extent of the Operator path's overlap with this file. **`specs/deployment/v1/operator.md` owns the rest**, including at least:

- Whether provisioning the spec ConfigMap is opt-in via the Operator's own configuration rather than unconditional. A diagnostic ConfigMap appearing in a production namespace without the customer asking for it is the kind of surprise that draws change-control friction, so the default matters.
- **How Operator customers set preferences that other tiers set as chart values.** This is a real gap, not a formality: `redaction.includeSchema` and the previous-container logs opt-in are chart values, and Operator customers do not install the chart. As things stand, the zero-config tier has no way to opt out of including schema/SDL — which is likely to matter most to exactly the customers who chose the Operator.
- Which targeting values the Operator populates, and from what, so the one-spec guarantee above is verifiable rather than asserted.
- **The Operator's metrics port and bind address**, stated as fact. The base spec targets a fixed `:9090` taken from the official Helm chart; whether the Operator matches it is a convention Apollo defines and therefore knowable, not an environmental unknown to be hedged. If it differs, either the Operator populates the port when it writes the spec or the base spec carries a second known default. See `specs/collection/base_spec.md` → Prometheus metrics.
- Whether the Operator pins or tracks a collection engine version for the local plugin its customers still have to install.

### Service mesh environments (`mode: job`)

**Decision: the Job pod runs outside the mesh. The chart disables sidecar injection on the Job by default** (`sidecar.istio.io/inject: "false"`, `linkerd.io/inject: disabled`, and the equivalent for other meshes), exposed as `job.sidecarInjection` for customers who need to override it.

**This applies to `mode: job` only, because it is the only mode where we create a pod.** There is no equivalent decision for `mode: local` or the Operator path: collection runs as a process on the invoking user's machine, so there is no pod spec to annotate and nothing to opt out of. Being outside the mesh is simply a fact of running from a laptop, not a choice a spec can make.

It is a decision for `mode: job` specifically because mesh injection is **automatic**. A mutating admission webhook adds a sidecar to any pod created in a mesh-enabled namespace, so a Job we create in the router's namespace gets one unless it explicitly declines. Not deciding is therefore not neutral — it selects injection, which is the option with the worse failure mode below.

Note that this decision governs only whether *our* pod joins the mesh. What a mesh does to collection when it blocks a collector — which sections come back empty, and why only the Prometheus scrape is exposed — is collection behavior, specified in `specs/collection/base_spec.md` → Service mesh and proxy environments, and it applies to both modes equally.

The tradeoff is between two failure modes of very different severity.

**Injecting a sidecar risks the Job never completing.** A Job's pod is expected to terminate when its work finishes, and an injected sidecar that keeps running prevents that — the collection finishes, the bundle is written, and the pod sits in `Running` forever instead of reaching `Completed`. That leaves a stuck workload in the customer's production namespace and no clean signal that collection succeeded. For a diagnostic tool whose central promise is that it is safe to run against a production router, leaving debris behind is the worse outcome, and it fails the whole path rather than one section of the bundle.

**Running outside the mesh costs only the metrics scrape, and costs it no more than `mode: local` already does.** Everything else reaches its data through the Kubernetes API server or cAdvisor, which the mesh does not sit in front of — `logs`, `clusterResources`, `containerMetrics`, `configMap` are all unaffected by an un-injected pod. The one collector that talks directly to a router port is the Prometheus scrape, and a mesh enforcing strict mTLS will reject it. But that is *already* true of `mode: local`, where collection runs from the user's machine — also outside the mesh. So disabling injection does not make the Job path worse than the documented baseline; it makes the two paths behave identically, which is the property the two modes are supposed to have.

**The empty metrics section must be attributable.** The chart knows whether it disabled injection, so that fact is recorded in `meta.json`. Without it, a mesh-blocked scrape is indistinguishable from a disabled exporter, and an empty section with no explanation is precisely what the collection spec is designed to avoid.

**Rejected: inject the sidecar so the scrape works, and terminate it after collection.** The usual mechanism is having the collection container signal the proxy's admin endpoint to quit once it is done. Rejected for v1: it couples our Job image to a specific mesh's admin API and version, needs per-mesh handling, and turns a clean "run and exit" into a teardown sequence with its own failure modes — all to recover one optional, best-effort section of the bundle. Kubernetes-native sidecars (init containers with `restartPolicy: Always`) solve the underlying lifecycle problem properly, and once a customer's cluster and mesh both support them, in-mesh collection becomes a reasonable thing to revisit through `job.sidecarInjection`.

**Required before `mode: job` is considered done:** a test in a mesh-enabled cluster with strict mTLS, confirming that the Job completes, the bundle is produced, the non-metrics collectors populate normally, and the empty metrics section is explained in `meta.json`.

## Cluster footprint

| Path | Standing footprint |
| --- | --- |
| Apollo Operator | The Operator-provisioned spec ConfigMap |
| `mode: local` | Spec ConfigMap + Helm release metadata |
| `mode: job` | Spec ConfigMap + Helm release metadata + ServiceAccount/Role/RoleBinding; the Job itself is transient |

Collection adds nothing beyond this: it is a single point-in-time snapshot packaged into a `.tar.gz`, and nothing from the collection run persists in the cluster after it completes.

The footprint is minimal but **not zero**, and this is a real adoption consideration rather than a footnote. Installing the chart creates a persistent object in a production cluster, so customers with strict change-control processes for anything touching production may hit friction. The tradeoff runs the other way once installed: subsequent collections are just `kubectl support-bundle --load-cluster-specs`, with no reinstall. Customers who want nothing left behind can `helm uninstall` after collecting; customers who expect to collect repeatedly should leave it installed.

## Permissions

**Installing the chart** requires permission to create ConfigMaps in the target namespace, plus — for `mode: job` — ServiceAccounts, RBAC objects, and Jobs. This is the same level of access needed to install the router itself.

**Running the collection** requires read access to the router's namespace. Where that access comes from is the only difference between the two modes:

| | `mode: local` | `mode: job` |
| --- | --- | --- |
| Identity | The invoking user's existing kubectl credentials | A namespace-scoped ServiceAccount created by the chart |
| Who runs it | The customer | A platform team member, via the Job |

The permissions themselves are the same in both cases, and follow from what the base spec's collectors need:

- **Namespace-scoped** (Role + RoleBinding in the router's namespace):
  - `pods`, `pods/log` — read-only, for pod status and log collection
  - `deployments` — read-only, for cluster resource collection
  - `configmaps` — read-only, for the router config read
- **Cluster-scoped** (ClusterRole + ClusterRoleBinding):
  - `nodes` — read-only, required by `containerMetrics` for cAdvisor container CPU/memory metrics. Node objects are not namespaced, so there is no namespace-scoped equivalent.

Read-only node access is the **only** permission that extends beyond the router's namespace. Everything else is confined to it. Both sets are documented explicitly so a customer with a strict security review can approve exactly what is granted, and can decline node access (losing cAdvisor memory/CPU metrics) without giving up the rest of the bundle.

### Permissions deliberately *not* required

Stated explicitly, because a security reviewer benefits from knowing what is absent, and because an unnoticed addition here would expand what customers have already approved:

- **`pods/exec` is not required.** Nothing in the v1 base spec executes inside the router container. The two router env vars that an earlier design read by exec — `APOLLO_GRAPH_REF` and `APOLLO_ROUTER_OFFICIAL_HELM_CHART` — are read from the pod spec that `clusterResources` already collects. See `specs/collection/base_spec.md` → Router env vars: read from the pod spec, which sets the two mechanisms side by side.
- **No write permission of any kind is required for collection.** Every collector reads. The chart install needs create permissions for its own objects; collection itself does not.
- **Secret read access is not required.** No collector reads Secret data, which is what makes the `APOLLO_KEY` guarantee structural rather than dependent on a redactor.

**This list may not hold forever, and a change to it is a change customers must re-approve.** If a future collector needs `pods/exec` — a heavier spec profiling memory through the router's diagnostics plugin is the obvious candidate — that is a deliberate expansion of the RBAC ask, not an implementation detail. It belongs in the PR description and in the customer-facing permissions documentation, and for a heavier spec it is a reason to ship that capability as a *separate* spec with its own permissions rather than growing the base spec's footprint. See `specs/architecture.md` → Specs.

## Bundle retrieval

For `mode: local`, the bundle lands on the invoking user's disk — the degenerate storage case, requiring no design.

For `mode: job`, no user is present to receive the bundle, which forces the question explicitly. The retrieval mechanism — mounted volume versus object storage — **is not settled in v1** and is specified in `specs/storage/`, not here. Storage is a layer; this spec covers only where collection executes.

## Rejected alternatives

**Publish static specs as OCI artifacts and pass customer values as CLI flags.** The original design published two specs (`oci://registry.apollo.dev/router-diagnostics-operator-spec` and `.../router-diagnostics-spec`) and had non-Operator customers invoke `kubectl support-bundle ./router-diagnostics-spec.yaml --namespace production --selector app=my-router`. This does not work: `kubectl support-bundle` accepts spec sources, not collector parameters, so `--selector` and `--namespace` cannot reach a collector. Customer-specific values must be templated into the spec, which requires a values-driven mechanism — the chart. Publishing a spec as an OCI artifact remains viable as a *source* mechanism, but cannot serve any tier that needs customer values templated in.

**A separate spec per deployment tier.** Rejected — v1 ships one spec, populated per tier. See [One spec, populated three ways](#one-spec-populated-three-ways) above for the reasoning.

**Ship only `mode: job` in v1, so Apollo pins the collection engine for everyone.** Considered because the Job path controls the engine version and the local paths do not (see [Collection engine version](#collection-engine-version)). Rejected: it would raise the privilege floor for every customer rather than lowering it, which inverts what the Job is for.

`mode: job` requires **more** access than `mode: local`, not less. Local invocation needs read access via the user's own kubeconfig. The Job additionally requires creating a Job, a ServiceAccount, a Role and RoleBinding, and — because `containerMetrics` needs `nodes` — a ClusterRole and ClusterRoleBinding. Cluster-scoped object creation is precisely what a namespace-limited engineer lacks. Kubernetes also prevents RBAC escalation: a user cannot create a Role granting permissions they do not themselves hold, absent the `escalate` verb. So standing up the Job's RBAC requires an installer who already has everything the Job will be granted.

`mode: job` is therefore not a lower-privilege path but a **delegation** path: the person who wants the bundle cannot get it, so someone with more access collects on their behalf. Making it the only mode would mean every customer — including those who could simply run the collection themselves in two commands — needs cluster-scoped RBAC creation rights first.

It would also break the Operator tier's zero-config story, which invokes the plugin locally, and remove the lowest-footprint path (no ServiceAccount, no RBAC objects, no Job).

The version asymmetry is real, but it argues for something narrower than descoping: prefer the Job where reproducibility matters, and manage the local paths with a tested floor and a documented minimum.

**Separate mechanisms for local invocation and restricted-access clusters.** Two delivery paths (a published spec for local use, a separate Job manifest for restricted clusters) would duplicate the spec in two places and let them drift. One chart with a `mode` value renders the same spec either way, so the collection definition has exactly one source.

**Do not support raw-manifest / custom deployments in v1.** This was the initial recommendation, on the grounds that the customer must know and supply all three values (`namespace`, `selector`, `configMapName`) themselves. It was rejected in favor of supporting the tier: the chart already exists for the official-chart tier, and exposing the two additional values costs nothing structurally. The cost is real but is borne by the customer who chose a custom deployment, and it is bounded — three values they already know, versus no support at all. `specs/user_experience.md` documents the raw-manifest path as supported.

**Accept an optional `metricsPort` value so non-official-chart tiers get Prometheus metrics.** Deferred, not adopted for v1. The `http` collector targets the official chart's known `:9090/metrics`; other tiers return empty rather than failing, consistent with the base spec's graceful degradation. Adding `metricsPort` later does not require rework, so v1 keeps the values surface smaller.

**Exec into the container to read the router config.** Needs the same customer-supplied input as the ConfigMap read (a mount path instead of a name), plus `pods/exec`, plus an actual exec into a container — to produce the same "config as written" result the ConfigMap read gets unprivileged. Its one genuine advantage is reading the file as it truly exists on disk, which catches configs that are not ConfigMap-backed at all (Secret-mounted, written by an init container, or baked into the image). Not worth the cost in v1. See `specs/collection/base_spec.md`.
