# Deployment — v1 (on-demand collection)

v1 deploys **on-demand (flare-style) collection only**. Scheduled and threshold-triggered collection, and the standing workloads they require, are part of v2.

This spec answers for v1: which deployment tiers are supported, what each tier requires from the customer, where collection executes, what footprint it leaves in the cluster, and what permissions it needs.

v1 is **Kubernetes-only**. ECS, Fargate, and standalone VM deployments are out of scope. All data stays in customer infrastructure; nothing is sent to Apollo.

**Scope:** this file covers the `router-diagnostics` chart and the deployment tiers that use it. **Apollo Operator deployment is specified in `specs/deployment/v1/operator.md`**. Anything specific to how the Operator provisions, configures, or gates the spec belongs in that file, not this one.

---

## The constraint that shapes everything here

`kubectl support-bundle` takes [spec *sources*](https://troubleshoot.sh/docs/support-bundle/collecting) — a file, URL, OCI artifact, or Kubernetes Secret/ConfigMap — **not collector parameters.** Customer-specific values (namespace, pod selector, ConfigMap name, redaction preferences) must therefore live *inside the spec YAML itself*. There is no invocation-time flag that can supply them: the one flag that accepts arbitrary key-values, `--metadata`, only attaches bundle-labelling metadata (it lands at `metadata/user.json`) and does not feed collectors.

Every deployment decision below follows from this. A customer-specific value reaches a collector only by being templated into the rendered spec, which is what makes a values-driven Helm chart the delivery mechanism rather than a published static spec plus CLI flags.

---

## One spec, populated three ways

**v1 ships exactly one spec.** There is a single base spec definition, authored once, and it is the only collection artifact v1 produces. What differs across deployment tiers is *who fills in its targeting values* — the Operator, or the chart from customer-supplied values — not which spec runs.

This is worth stating plainly, because a per-tier spec is the obvious alternative — a self-contained Operator variant plus a parameterized variant for everyone else — and it is rejected: two artifacts describing the same collection will drift, and a drifted spec means Operator and non-Operator customers silently send support different bundles from the same tool version. Any change to what is collected must land in one place. If a tier's needs ever cannot be met by populating the one spec's values, that is a signal to revisit the targeting parameters rather than to fork the spec.

## Deployment tiers

| Deployment tier | Support in v1 | Customer supplies | How the tool locates the router |
| --- | --- | --- | --- |
| **Apollo Operator** | Full support, zero config | Nothing | The Operator populates the spec's targeting values from conventions it already knows — see `specs/deployment/v1/operator.md` |
| **Official Apollo router Helm chart** | Full support | `namespace` | Standard chart label `app.kubernetes.io/name=router`; ConfigMap name, config key, and ports are fixed by the chart |
| **Raw manifests / custom deployment** | Supported | `namespace`, `selector`, `configMapName` | Entirely from customer-supplied values — no convention applies |

`namespace` is required at every non-Operator tier and cannot be eliminated, and it must be templated into **every** collector that accepts it — not only the ones that obviously need targeting. The field name differs by collector, and so does the consequence of omitting it:

| Collector | Field | If omitted |
| --- | --- | --- |
| `logs`, `configMap` | `namespace` (string) | Falls back to the invoking kubectl context's namespace. If that context is not pointed at the router, the collector silently searches the wrong place and returns empty. |
| `clusterResources` | **`namespaces` (list)** | Falls back to **every namespace in the cluster.** |

Both failure modes are silent, and they fail in opposite directions — which is why this is called out rather than left to whoever writes the YAML.

**The `clusterResources` case is the more serious of the two and the easier to miss**, because the field is named differently (`namespaces`, plural, taking a list) and because omitting it produces *more* data rather than less, so nothing about the resulting bundle looks broken. Confirmed from [the collector source](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/collect/cluster_resources.go#L132): with no `namespaces` set and no namespace otherwise supplied, it enumerates all namespaces and collects from each. Since `clusterResources` gathers ConfigMaps with their full `data`, an unscoped run puts every ConfigMap in the cluster — unrelated teams' application config included — into a bundle the customer may hand to Apollo.

A namespace-scoped ServiceAccount would make the cluster-wide listing fail, but that is not a safeguard to rely on: `mode: local` could run as an identity with broad read access, in which case the wider collection succeeds quietly. The chart must render `namespaces: [<namespace>]` — the required singular value as a single-element list — and this is worth a regression check in the test matrix: run collection as a cluster-admin identity and assert the bundle contains nothing from outside the router's namespace.

### What the official Apollo Helm chart makes inferable

Confirmed at `v2.17.0` — the same pin used throughout `specs/collection/base_spec.md` — by rendering `oci://ghcr.io/apollographql/helm-charts/router` with `helm template`. These are the conventions the chart tier relies on:

| Information | Finding |
| --- | --- |
| ConfigMap name | Exactly the Helm release name (release `my-router` → ConfigMap `my-router`) — no templated suffix or hash |
| Config key in the ConfigMap | `configuration.yaml` |
| Mount path in the container | `/app/configuration.yaml` |
| Standard labels | `app.kubernetes.io/name=router` on every chart resource, including the ConfigMap |
| Health check port | `8088`, paths `/health?live` and `/health?ready` |
| App traffic port | Container `4000`, exposed on the Service as port `80` |
| `APOLLO_GRAPH_REF` | A plain literal env var on the container |
| `APOLLO_KEY` | Present as an env var, but sourced via `secretKeyRef` from a **separate Secret** (`managedFederationApiKey`) — not a literal, and structurally separated from the config ConfigMap, so a ConfigMap-only read cannot expose it |
| Deployment-type signal | `APOLLO_ROUTER_OFFICIAL_HELM_CHART=true` is set as an env var — the same variable `fleet_detector.rs` checks (`OFFICIAL_HELM_CHART_VAR`) to report `deployment_type=official_helm_chart` |

Metrics values are **not** exposed by default; they appear when `serviceMonitor.enabled=true`, which confirms Prometheus is opt-in at the chart level as well as in `router.yaml`:

| Information | Finding |
| --- | --- |
| Metrics container port | `9090` (matches the `containerPorts.metrics: 9090` default) |
| Metrics Service port | `9090`, `targetPort: metrics` |
| Path | `/metrics` (confirmed via the Deployment annotation `prometheus.io/path: /metrics`) |
| ServiceMonitor | Rendered only when `serviceMonitor.enabled: true`; targets `port: metrics` |
| What actually turns metrics on | `router.configuration.telemetry.exporters.metrics.prometheus.enabled: true` **and** `.listen` inside the router config values — not `serviceMonitor.enabled` alone |

The label-based targeting is the load-bearing finding: because the chart applies `app.kubernetes.io/name=router` to every resource, collectors can target by label rather than by release name, which is why this tier needs only `namespace`.

## Prerequisite: the collection binary

**Installing the chart is not sufficient to collect a bundle.** The chart's only job is to get a populated spec into the cluster; it does not deliver the thing that runs it. troubleshoot.sh is explicit that collection is client-side — *"This does not deploy anything to the cluster, it's all client-side code"* — so something must supply the `support-bundle` binary, and which side that is depends on the path:

| Path | Who supplies the binary | Customer prerequisite |
| --- | --- | --- |
| Apollo Operator | The invoking user's machine | Install the plugin |
| `mode: local` | The invoking user's machine | Install the plugin |
| `mode: job` | The Job's container image | None — the image ships the binary |

For the two local paths, the customer installs it once, either as a kubectl plugin via krew:

```bash
kubectl krew install support-bundle
```

or as a standalone binary, for CI or for machines without `krew`:

```bash
curl -L https://github.com/replicatedhq/troubleshoot/releases/latest/download/support-bundle_linux_amd64.tar.gz | tar xzvf -
```

Installing the plugin puts a single binary in the user's path and deploys nothing to the cluster. `kubectl support-bundle` *is* that binary — this is a genuine second prerequisite alongside the chart, not an implementation detail, and it is the step most likely to be missed because the chart install appears to complete the setup.

Because collection is client-side, `mode: job` requires an image containing the binary. Apollo owns and publishes that image (see `specs/architecture.md`).

### Collection engine version

The two paths differ in who controls the engine version, and this is a real asymmetry rather than a packaging detail:

| Path | Engine version | Controlled by |
| --- | --- | --- |
| `mode: job` | Pinned by the image tag | Apollo |
| `mode: local`, Operator | Whatever plugin the user installed — `krew` installs latest | The customer |

**The plugin version cannot be pinned by us.** It lives on the customer's machine, outside every artifact we deliver, and `krew` tracks latest. There is no mechanism to force a version, and the spec should not pretend otherwise.

That is acceptable because the exposure is a function of *what the spec uses*, not of plugin drift in the abstract. The base spec uses only long-established collectors — `logs`, `clusterResources`, `nodeMetrics`, `http`, `configMap`, `helm`. The risk materializes only when the spec adopts a newer collector or field. Hence the rule:

**Adopting a collector or field that raises the minimum supported troubleshoot.sh version is a deliberate, reviewed spec change, called out as such in the PR.** This converts an ambient compatibility risk into a change-control step, which is where it belongs.

Four supporting requirements:

1. **A tested floor.** The spec declares a minimum supported troubleshoot.sh version, and that number comes from a verified run in the test matrix — not from a guess. **Open:** the floor is not yet determined; it should be set when the base spec is first validated against the testing matrix.
2. **Test the floor and a current release.** Drift cuts both ways. A plugin *newer* than anything we tested can change behavior or default redaction, and that direction is unbounded because `krew` moves on its own schedule.
3. **The engine already records its own version — read it, don't duplicate it.** Nothing enforces a minimum client-side (the plugin will not check a version field we put in the spec), so the mitigation is diagnostic rather than preventive: when a bundle comes back short, support needs to see which engine produced it. That is already available. Every bundle contains **`version.yaml`**, written by troubleshoot.sh with the version that produced it. What the spec must supply is the other half of the comparison — the declared floor, carried as `min_troubleshoot_version` in `meta.json`. See `specs/collection/meta_json.md`.
4. **Offer a pinned download.** `krew` is the easy path and tracks latest; the standalone binary is the reproducible path, because the release URL can name a specific tag instead of `latest`. Customers in CI or under strict change control should be pointed at a pinned tag.

A consequence worth stating: **`mode: job` is the more reproducible path**, since Apollo pins the engine. That is a reason to prefer the Job in our own test matrix, and a reason to recommend it to a customer who wants a known-good collection to send during a support engagement — not a reason to make it the only mode. See [Rejected alternatives](#rejected-alternatives).

### Verified against the troubleshoot.sh docs

Two mechanics this deployment story depends on, confirmed rather than assumed:

- **Bare `--load-cluster-specs` is valid.** It runs with no positional spec argument, collecting only from specs discovered in the cluster. Every invocation in this spec relies on that.
- **Discovery is by label** — a ConfigMap or Secret must carry `troubleshoot.sh/kind: support-bundle`, which is the label the chart's spec ConfigMap sets.
- **The `SupportBundle` and `Redactor` documents are two separate `data` keys on that same labelled object.** Confirmed from source: `getSpecFromConfigMap`/`getSpecFromSecret` ([`loader.go#L280-297`](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/loader/loader.go#L280)) read specific named keys off the discovered ConfigMap or Secret — `constants.SupportBundleKey` (literally `support-bundle-spec`) and `constants.RedactorKey` (literally `redactor-spec`), per [`constants.go#L77-78`](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/constants/constants.go#L77). See `specs/collection/data_sanitization/overview.md` → How the `Redactor` document is delivered.

## One chart, two modes

Non-Operator customers install a single Helm chart, `router-diagnostics`, with a required `mode` value. Rather than building separate mechanisms for local invocation and for restricted-access clusters, one chart serves both:

- **`mode: local`** — renders only the spec, as a cluster ConfigMap. The customer runs the collection themselves with their own kubectl credentials.
- **`mode: job`** — renders the same spec ConfigMap **plus** a Job and its ServiceAccount/RBAC, which runs the collection in-cluster. For customers whose kubectl access to production is restricted and who need a platform team to run it on their behalf.

Both modes render the spec as a ConfigMap labelled for `--load-cluster-specs` to discover. Both use the same spec and the same collection engine; only who runs it, where, and how the bundle is retrieved differ.

```
router-diagnostics/
├── templates/
│   ├── spec-configmap.yaml     # always rendered
│   ├── job.yaml                # rendered only if mode: job
│   └── job-rbac.yaml           # rendered only if mode: job
└── values.yaml
```

```yaml
# templates/spec-configmap.yaml — always rendered
apiVersion: v1
kind: ConfigMap
metadata:
  name: router-diagnostics-spec
  labels:
    troubleshoot.sh/kind: support-bundle
data:
  support-bundle-spec: |
    {{ include "router-diagnostics.spec" . }}
  redactor-spec: |
    {{ include "router-diagnostics.redactors" . }}
```

Both keys are required to be named exactly this — troubleshoot.sh's loader looks up `support-bundle-spec` and `redactor-spec` specifically, not an arbitrary key the chart gets to pick (see [Verified against the troubleshoot.sh docs](#verified-against-the-troubleshootsh-docs) above). `redactor-spec` holds the `kind: Redactor` document specified in `specs/collection/data_sanitization/`.

```yaml
# templates/job.yaml — only rendered if mode: job
{{- if eq .Values.mode "job" }}
apiVersion: batch/v1
kind: Job
...
{{- end }}
```

### Chart values

**This table is the complete `values.yaml` interface. It is the single reference — no other document defines a chart value.** Other specs may explain what a value *does* to collection behavior, but the interface itself is defined here and nowhere else, because a values surface split across documents is one that ends up incomplete in both.

Values are grouped by concern so that targeting, execution, redaction, and collection behavior read as distinct groups rather than a flat list:

| Value | Required | Default | Applies to | Purpose |
| --- | --- | --- | --- | --- |
| `namespace` | Yes | — | All non-Operator tiers | The router's namespace. Rendered into every collector that accepts it, including `clusterResources.namespaces` as a single-element list. Never rely on the kubectl context fallback. |
| `mode` | Yes | — | All non-Operator tiers | `local` or `job` |
| `selector` | Raw-manifest tier only | The official chart's `app.kubernetes.io/name=router` label | Raw manifests / custom | Pod label selector, e.g. `app=my-router` |
| `configMapName` | Raw-manifest tier only | Label-based targeting, no name needed | Raw manifests / custom | Name of the ConfigMap holding the router config |
| `redaction.includeSchema` | No | `true` | All tiers | Include graph schema/SDL in the bundle; `false` strips it entirely |
| `job.sidecarInjection` | No | `false` | `mode: job` only | Whether the Job pod joins a service mesh. Disabled by default so the Job reliably reaches `Completed` — see [Service mesh environments](#service-mesh-environments-mode-job) |
| `logs.maxAge` | No | Unset — no age cap | All tiers | Maps to the `logs` collector's `limits.maxAge`. How far back to reach, e.g. `2h` |
| `logs.maxLines` | No | `10000` (troubleshoot.sh default) | All tiers | Maps to `limits.maxLines`. Lines from newest per container |

#### Values deliberately not exposed

Naming what is fixed matters as much as naming what is configurable, because each of these was a candidate:

| Not a value | Why |
| --- | --- |
| Previous-container logs | **Not configurable, and not optional.** The [`logs` collector](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/apis/troubleshoot/v1beta2/collector_shared.go#L80) has no `previous` field; it [always requests previous-container logs](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/collect/logs.go#L200) after the current ones and writes them to `<name>-previous.log`, silently skipping when there is no previous container. There is nothing to expose. |
| `logs.timestamps` | Fixed to `true`, not left to the customer. Log timestamps are how a bundle is correlated with an incident timeline, and they carry more weight now that no precise collection timestamp is recorded — see `specs/collection/meta_json.md` → Collection time. |
| `logs.maxBytes` | Left at the troubleshoot.sh default (5 MB per file). Exposed only if bundle size becomes a real complaint. |
| `metricsPort` | Deferred — see [Rejected alternatives](#rejected-alternatives). |
| `routerReleaseName` | Deferred — see [Rejected alternatives](#rejected-alternatives). |

`redaction.includeSchema` is nested rather than top-level deliberately. It is the only customer-configurable redactor today, and grouping keeps room for future ones without cluttering the chart's top-level values. Everything else — built-in credential/token redactors and Apollo's custom JWT, auth-config, header-value, operation-body, and subgraph-URL redactors — is fixed with no configuration. See `specs/collection/data_sanitization/`.

### Service mesh environments (`mode: job`)

**Decision: the Job pod runs outside the mesh. The chart disables sidecar injection on the Job by default** (`sidecar.istio.io/inject: "false"`, `linkerd.io/inject: disabled`, and the equivalent for other meshes), exposed as `job.sidecarInjection` for customers who need to override it.

**This applies to `mode: job` only, because it is the only mode where we create a pod.** There is no equivalent decision for `mode: local` or the Operator path: collection runs as a process on the invoking user's machine, so there is no pod spec to annotate and nothing to opt out of. Being outside the mesh is simply a fact of running from a laptop, not a choice a spec can make.

It is a decision for `mode: job` specifically because mesh injection is **automatic**. A mutating admission webhook adds a sidecar to any pod created in a mesh-enabled namespace, so a Job we create in the router's namespace gets one unless it explicitly declines. Not deciding is therefore not neutral — it selects injection, which is the option with the worse failure mode below.

Note that this decision governs only whether *our* pod joins the mesh. What a mesh does to collection when it blocks a collector — which sections come back empty, and why only the Prometheus scrape is exposed — is collection behavior, specified in `specs/collection/base_spec.md` → Service mesh and proxy environments, and it applies to both modes equally.

The tradeoff is between two failure modes of very different severity.

**Injecting a sidecar risks the Job never completing.** A Job's pod is expected to terminate when its work finishes, and an injected sidecar that keeps running prevents that — the collection finishes, the bundle is written, and the pod sits in `Running` forever instead of reaching `Completed`. That leaves a stuck workload in the customer's production namespace and no clean signal that collection succeeded. For a diagnostic tool whose central promise is that it is safe to run against a production router, leaving debris behind is the worse outcome, and it fails the whole path rather than one section of the bundle.

**Running outside the mesh costs only the metrics scrape, and costs it no more than `mode: local` already does.** Everything else reaches its data through the Kubernetes API server or the kubelet, which the mesh does not sit in front of — `logs`, `clusterResources`, `nodeMetrics`, `configMap` are all unaffected by an un-injected pod. The one collector that talks directly to a router port is the Prometheus scrape, and a mesh enforcing strict mTLS will reject it. But that is *already* true of `mode: local`, where collection runs from the user's machine — also outside the mesh. So disabling injection does not make the Job path worse than the documented baseline; it makes the two paths behave identically, which is the property the two modes are supposed to have.

**The chart records what it can about the empty metrics section, though not a full explanation.** It knows whether it disabled injection, and that fact is recorded in `meta.json`'s `sidecar_injection_disabled` field. That rules out one specific cause — interception via the Job's own mesh membership — but does not, on its own, confirm a mesh issue exists or attribute the section fully; disambiguating a mesh-blocked scrape from a disabled or misconfigured exporter still requires reading the collected `router.yaml` alongside it, per `specs/collection/base_spec.md` → Service mesh and proxy environments.

**Rejected: inject the sidecar so the scrape works, and terminate it after collection.** The usual mechanism is having the collection container signal the proxy's admin endpoint to quit once it is done. Rejected for v1: it couples our Job image to a specific mesh's admin API and version, needs per-mesh handling, and turns a clean "run and exit" into a teardown sequence with its own failure modes — all to recover one optional, best-effort section of the bundle. Kubernetes-native sidecars (init containers with `restartPolicy: Always`) solve the underlying lifecycle problem properly, and once a customer's cluster and mesh both support them, in-mesh collection becomes a reasonable thing to revisit through `job.sidecarInjection`.

**Required before `mode: job` is considered done:** a test in a mesh-enabled cluster with strict mTLS, confirming that the Job completes, the bundle is produced, the non-metrics collectors populate normally, and `sidecar_injection_disabled` is recorded correctly in `meta.json`.

## Cluster footprint

| Path | Standing footprint |
| --- | --- |
| Apollo Operator | The Operator-provisioned spec ConfigMap |
| `mode: local` | Spec ConfigMap + Helm release metadata |
| `mode: job` | Spec ConfigMap + Helm release metadata + ServiceAccount/Role/RoleBinding; the Job itself is transient |

Collection adds nothing beyond this: it is a single point-in-time snapshot packaged into a `.tar.gz`, and nothing from the collection run persists in the cluster after it completes.

The footprint is minimal but **not zero**, and this is a real adoption consideration rather than a footnote. Installing the chart creates a persistent object in a production cluster, so customers with strict change-control processes for anything touching production may hit friction. The tradeoff runs the other way once installed: subsequent collections are just `kubectl support-bundle --load-cluster-specs`, with no reinstall. Customers who want nothing left behind can `helm uninstall` after collecting; customers who expect to collect repeatedly should leave it installed.

## Permissions

**Installing the chart with `mode: local`** requires permission to create a ConfigMap in the target namespace — the same level of access needed to install the router itself.

**Installing the chart with `mode: job` requires more.** Beyond the ConfigMap, it needs to create a Job, a namespace-scoped ServiceAccount, a Role and RoleBinding, and — because `nodeMetrics` needs `nodes`, `nodes/proxy`, and `nodes/stats` — **a ClusterRole and ClusterRoleBinding.** Creating cluster-scoped RBAC objects is a materially broader capability than anything installing the router requires. It is not, however, a *larger permission set* than `mode: local` needs — the same three node grants are required of the `mode: local` user's own kubeconfig identity too, or `nodeMetrics` fails there just the same. What `mode: job` adds is the right to **create** RBAC objects carrying those permissions, so they can be granted to something other than the invoking user. Kubernetes prevents RBAC escalation — a user cannot create a Role granting permissions they do not themselves hold, absent the `escalate` verb — so whoever installs the chart in `mode: job` must already hold all three node permissions themselves. This asymmetry is why `mode: job` is a **delegation** path rather than a lower-privilege one: see [Rejected alternatives](#rejected-alternatives) → Ship only `mode: job` in v1.

**Running the collection** requires read access to the router's namespace. Where that access comes from is the only difference between the two modes:

| | `mode: local` | `mode: job` |
| --- | --- | --- |
| Identity | The invoking user's existing kubectl credentials | A namespace-scoped ServiceAccount created by the chart |
| Who runs it | The customer | A platform team member, via the Job |

The permissions themselves are the same in both cases, and follow from what the base spec's collectors need:

- **Namespace-scoped** (Role + RoleBinding in the router's namespace):
  - `pods`, `pods/log` — read-only, for pod status and log collection
  - `deployments` — read-only, for cluster resource collection
  - `configmaps` — read-only, for the router config read
- **Cluster-scoped** (ClusterRole + ClusterRoleBinding):
  - `nodes` — **list**, to resolve node names for the `nodeMetrics` collector
  - `nodes/proxy` — **get**, required unconditionally by the API server for any request proxied through it to a kubelet, regardless of which path follows. This is the permission `nodeMetrics` uses to reach the kubelet at all. Node objects are not namespaced, so there is no namespace-scoped equivalent, and `nodeMetrics` cannot be scoped to only the router's nodes.
  - `nodes/stats` — **get**, required separately by the kubelet's own authorization check specifically for the stats endpoint `nodeMetrics` calls. This is layered on top of `nodes/proxy`, not a substitute for it — declining one without the other still fails.

Node access is the **only** permission set that extends beyond the router's namespace. Everything else is confined to it. Both sets are documented explicitly so a customer with a strict security review can approve exactly what is granted.

**`nodes/proxy` is the entry worth a reviewer's closest attention, and it is decline-able (along with `nodes/stats`, which is meaningless without it).** It is a materially heavier grant than reading node objects — Kubernetes' own RBAC good-practices documentation states that `get` on `nodes/proxy` "provides access to privileged kubelet APIs that can retrieve container logs or execute and attach to pod processes... This access bypasses audit logging and admission control," and is explicitly "not a read-only permission." What this tool does with the grant is read-only — it only ever calls the kubelet's stats endpoint — but the grant itself authorizes more than that one use, and a reviewer should evaluate it as such rather than as a narrowed, tool-specific capability. It is requested for exactly one purpose: container memory and CPU trajectory for customers who have not enabled the router's Prometheus exporter, which is the only other source for that signal. Declining `nodes/proxy` and `nodes/stats` still leaves OOM kill occurrences and last state, restart counts, configured limits, and node pressure conditions — all of which come from `clusterResources` — plus process-level memory and CPU when the exporter is enabled. See `specs/collection/base_spec.md` → RBAC: what `nodeMetrics` actually requires.

### Permissions deliberately *not* required

Stated explicitly, because a security reviewer benefits from knowing what is absent, and because an unnoticed addition here would expand what customers have already approved:

- **`pods/exec` is not required.** Nothing in the v1 base spec executes inside the router container. The two router env vars that would otherwise call for it — `APOLLO_GRAPH_REF` and `APOLLO_ROUTER_OFFICIAL_HELM_CHART` — are read from the pod spec that `clusterResources` already collects. See `specs/collection/base_spec.md` → Router env vars: read from the pod spec, which sets the two mechanisms side by side.
- **No write permission of any kind is required for collection.** Every collector reads. The chart install needs create permissions for its own objects; collection itself does not.
- **Secret read access is not required.** No collector reads Secret data, which is what makes the `APOLLO_KEY` guarantee structural rather than dependent on a redactor.

**This list may not hold forever, and a change to it is a change customers must re-approve.** If a future collector needs `pods/exec` — a heavier spec profiling memory through the router's diagnostics plugin is the obvious candidate — that is a deliberate expansion of the RBAC ask, not an implementation detail. It belongs in the PR description and in the customer-facing permissions documentation, and for a heavier spec it is a reason to ship that capability as a *separate* spec with its own permissions rather than growing the base spec's footprint. See `specs/architecture.md` → Specs.

## Rejected alternatives

**Publish static specs as OCI artifacts and pass customer values as CLI flags.** The appealing shape: publish the spec to a public registry and have customers invoke `kubectl support-bundle ./router-diagnostics-spec.yaml --namespace production --selector app=my-router`, with no chart and no cluster footprint. It does not work: `kubectl support-bundle` accepts spec sources, not collector parameters, so `--selector` and `--namespace` cannot reach a collector. Customer-specific values must be templated into the spec, which requires a values-driven mechanism — the chart. Publishing a spec as an OCI artifact remains viable as a *source* mechanism, but cannot serve any tier that needs customer values templated in.

**A separate spec per deployment tier.** Rejected — v1 ships one spec, populated per tier. See [One spec, populated three ways](#one-spec-populated-three-ways) above for the reasoning.

**Ship only `mode: job` in v1, so Apollo pins the collection engine for everyone.** Considered because the Job path controls the engine version and the local paths do not (see [Collection engine version](#collection-engine-version)). Rejected: it would raise the privilege floor for every customer rather than lowering it, which inverts what the Job is for.

`mode: job` requires **more** access than `mode: local` to install, not to run — see `## Permissions` above for why: the underlying permission set is identical, and what `mode: job` actually adds is the right to create RBAC objects on someone else's behalf, which Kubernetes' escalation rule ties to already holding those permissions. `mode: job` is therefore not a lower-privilege path but a **delegation** path: the person who wants the bundle cannot get it, so someone with more access collects on their behalf. Making it the only mode would mean every customer — including those who could simply run the collection themselves in two commands — needs cluster-scoped RBAC creation rights first.

It would also break the Operator tier's zero-config story, which invokes the plugin locally, and remove the lowest-footprint path (no ServiceAccount, no RBAC objects, no Job).

The version asymmetry is real, but it argues for something narrower than descoping: prefer the Job where reproducibility matters, and manage the local paths with a tested floor and a documented minimum.

**Separate mechanisms for local invocation and restricted-access clusters.** Two delivery paths (a published spec for local use, a separate Job manifest for restricted clusters) would duplicate the spec in two places and let them drift. One chart with a `mode` value renders the same spec either way, so the collection definition has exactly one source.

**Do not support raw-manifest / custom deployments in v1.** This was the initial recommendation, on the grounds that the customer must know and supply all three values (`namespace`, `selector`, `configMapName`) themselves. It was rejected in favor of supporting the tier: the chart already exists for the official-chart tier, and exposing the two additional values costs nothing structurally. The cost is real but is borne by the customer who chose a custom deployment, and it is bounded — three values they already know, versus no support at all. `specs/user_experience.md` documents the raw-manifest path as supported.

**Accept an optional `metricsPort` value so non-official-chart tiers get Prometheus metrics.** Deferred, not adopted for v1. The `http` collector targets the official chart's known `:9090/metrics`; other tiers return empty rather than failing, consistent with the base spec's graceful degradation. Adding `metricsPort` later does not require rework, so v1 keeps the values surface smaller.

**Accept an optional `routerReleaseName` value to disambiguate multiple router releases in one namespace, for the official-chart tier.** Deferred, not adopted for v1, but worth revisiting — the gap it would close is real, not hypothetical. Confirmed from source: [`_helpers.tpl`](https://github.com/apollographql/router/blob/v2.17.0/helm/chart/router/templates/_helpers.tpl) sets `app.kubernetes.io/instance: {{ .Release.Name }}` on every chart resource including the ConfigMap, and troubleshoot.sh's `configMap` collector ([`configmap.go#L127`](https://github.com/replicatedhq/troubleshoot/blob/v0.120.0/pkg/collect/configmap.go#L127)) will do a direct `Get` by exact name when the collector's `name:` field is set, in preference to selector-based listing.

The problem this would solve: `specs/collection/base_spec.md` → `router.yaml` capture documents that the `configMap` collector targets by `app.kubernetes.io/name=router` alone, with no per-release filter, so a namespace holding more than one router release (one per graph, a real pattern) has every release's ConfigMap collected, not just the one being diagnosed. This isn't a silent-drop problem — each match is written to its own uniquely-named file, so nothing is lost or overwritten — but it is an over-collection problem: a customer sharing a bundle for one graph's incident unknowingly also shares every other release's configuration from that namespace.

An optional `routerReleaseName` value, templated into the `configMap` collector's `name:` field when set (falling back to today's label-only `selector` when unset), would let a customer who knows they have more than one release in the namespace narrow to exactly the one they mean — while leaving the common single-release case exactly as zero-config as it is today. This deliberately does not reuse `configMapName`, which already exists for the raw-manifest tier: that value has to be an arbitrary customer-supplied literal because raw-manifest deployments have no Helm release convention guaranteeing any particular ConfigMap name, whereas `routerReleaseName` would leverage a convention specific to the official chart (ConfigMap name and `app.kubernetes.io/instance` are both exactly `.Release.Name`) — asking the customer for the release name they already know, rather than a ConfigMap name they'd have to look up.

Why deferred rather than added now: no customer has yet hit this in practice, and every value added to the chart's interface is a value that has to be documented, tested, and carried forward — see `## Chart values`'s framing above about keeping that surface as small as it can be. If this is picked up later, `specs/collection/base_spec.md` → `router.yaml` capture and `specs/collection/meta_json.md` → Multiple router releases in one namespace both currently describe the absence of any narrowing mechanism and would need updating in the same change, per `CLAUDE.md`'s reconcile-don't-diverge rule.

**Exec into the container to read the router config.** Needs the same customer-supplied input as the ConfigMap read (a mount path instead of a name), plus `pods/exec`, plus an actual exec into a container — to produce the same "config as written" result the ConfigMap read gets unprivileged. Its one genuine advantage is reading the file as it truly exists on disk, which catches configs that are not ConfigMap-backed at all (Secret-mounted, written by an init container, or baked into the image). Not worth the cost in v1 — this is the same tradeoff (RBAC and reliability cost vs. resolving indirected values) as the env-var `exec` removal decided in `specs/collection/base_spec.md` → Router env vars: read from the pod spec.
