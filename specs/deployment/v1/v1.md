# Deployment — v1 (on-demand collection)

This file is the technical reference for the `router-diagnostics` chart — deployment tiers, RBAC, and cluster footprint. For the step-by-step customer-facing setup flow, see `specs/user_experience.md`. For Apollo Operator deployment, see `specs/deployment/v1/operator.md`.

v1 deploys on-demand (flare-style) support bundle collection for Kubernetes deployments only.

## Deployment tiers

| Deployment tier | Customer supplies | How the tool locates the router |
| --- | --- | --- |
| **Apollo Operator** | Nothing | See `specs/deployment/v1/operator.md` |
| **Official Apollo router Helm chart** | `namespace` | Standard chart label `app.kubernetes.io/name=router`. ConfigMap name, config key, and ports are fixed by the chart |
| **Raw manifests / custom deployment** | `namespace`, `selector`, `configMapName` | Entirely from customer-supplied values — no convention applies |

## Collection modes

Every non-Operator deployment runs collection in one of two modes, set via the chart's `mode` value.

- **`mode: local`** — you run the collection yourself, with your own kubectl access. See [`mode: local`](#mode-local).
- **`mode: job`** — a Kubernetes Job runs the collection in-cluster, for teams whose kubectl access to production is restricted and who need a platform team to run it on their behalf. See [`mode: job`](#mode-job).

---

## Helm chart

Non-Operator customers install a single Helm chart, `router-diagnostics`, with a required `mode` value. Rather than building separate mechanisms for the two modes, one chart serves both: `mode: local` renders only the spec, as a cluster ConfigMap and `mode: job` renders the same spec ConfigMap plus a Job and its ServiceAccount/RBAC to run the collection in-cluster.

Both modes render the spec as a ConfigMap labeled for `--load-cluster-specs` to discover and both use the same spec. Only who runs it, where, and how the bundle is retrieved differ — see [`mode: local`](#mode-local) and [`mode: job`](#mode-job) below.

```
router-diagnostics/
├── templates/
│   ├── spec-configmap.yaml     # always rendered
│   ├── job.yaml                # rendered only if mode: job
│   └── job-rbac.yaml           # rendered only if mode: job
└── values.yaml
```

```yaml
# templates/spec-configmap.yaml — always rendered
apiVersion: v1
kind: ConfigMap
metadata:
  name: router-diagnostics-spec
  labels:
    troubleshoot.sh/kind: support-bundle
data:
  support-bundle-spec: |
    {{ include "router-diagnostics.spec" . }}
  redactor-spec: |
    {{ include "router-diagnostics.redactors" . }}
```

### Chart values common to both modes

| Value | Required | Default | Applies to | Purpose |
| --- | --- | --- | --- | --- |
| `namespace` | Yes | — | Official chart, raw manifest / custom | The router's namespace. Rendered into every collector that accepts it, including `clusterResources.namespaces` as a single-element list. Never rely on the kubectl context fallback. |
| `mode` | Yes | — | Official chart, raw manifest / custom | `local` or `job` |
| `selector` | Raw-manifest tier only | The official chart's `app.kubernetes.io/name=router` label | Raw manifests / custom | Pod label selector, e.g. `app=my-router` |
| `configMapName` | Raw-manifest tier only | Label-based targeting, no name needed | Raw manifests / custom | Name of the ConfigMap holding the router config |
| `logs.maxAge` | No | Unset — no age cap | Official chart, raw manifest / custom | Maps to the `logs` collector's `limits.maxAge`. How far back to reach, e.g. `2h` |
| `logs.maxLines` | No | `10000` (troubleshoot.sh default) | Official chart, raw manifest / custom | Maps to `limits.maxLines`. Lines from newest per container |

`mode`-specific values (`job.podAnnotations`, `job.podLabels`) are documented in [`mode: job`](#mode-job) below.

### troubleshoot.sh support-bundle version

The two paths differ in who controls the troubleshoot.sh support-bundle version:

| Path | support-bundle version | Controlled by |
| --- | --- | --- |
| `mode: job` | Pinned by the image tag | Apollo |
| `mode: local`, Operator | Whatever plugin the user installed — `krew` installs latest | The customer |

## `mode: local`

You run the collection yourself, with your own kubectl access.

If the router's metrics section comes back empty because collection runs outside a service mesh, see [Running outside the mesh doesn't have to mean losing metrics](#running-outside-the-mesh-doesnt-have-to-mean-losing-metrics).

### Prerequisite: the collection binary for `mode: local`

Collection runs from **the invoking user's own machine**, so the customer installs troubleshoot's `support-bundle` binary once, either as a kubectl plugin via krew:

```bash
kubectl krew install support-bundle
```

or as a standalone binary, for CI or for machines without `krew`:

```bash
curl -L https://github.com/replicatedhq/troubleshoot/releases/latest/download/support-bundle_linux_amd64.tar.gz | tar xzvf -
```

**The customer controls the troubleshoot.sh support-bundle version** in this mode (`krew` installs latest). See [troubleshoot.sh support-bundle version](#troubleshootsh-support-bundle-version) above for what that means for testing.

### Reaching `router-metrics` under `mode: local`

The router's metrics port is only reachable through its in-cluster Service DNS name (`<service>.<namespace>.svc.cluster.local`). `mode: local` runs `support-bundle` on the invoking user's own machine, outside the cluster's network, where that name does not resolve — so the `router-metrics` collector fails with a connection error, not an empty result, unless the customer bridges the two networks first. The rendered spec targets `localhost:9090` under `mode: local` for this reason. This is not required under `mode: job` — the Job's pod runs inside the cluster, where the Service DNS name resolves normally.

If skipped, the effect on the bundle is silent in a way that matters: the collector reports a connection error, not the "empty because not configured" case the rest of the bundle is designed around (see `specs/architecture.md` — Empty is not failure). `nodeMetrics` remains available as a fallback for container-level memory/CPU signal regardless (see `specs/collection/base_spec.md` → `nodeMetrics` is a fallback, not the preferred path).

**This is automated by a Helm plugin shipped alongside the chart**, rather than a standalone script the customer downloads and runs separately. The plugin follows the same one-time-install pattern already used for the `support-bundle` kubectl plugin (see [Prerequisite: the collection binary for `mode: local`](#prerequisite-the-collection-binary-for-mode-local) above):

```bash
helm plugin install https://github.com/apollographql/router-diagnostics-helm-plugin
```

This adds a `helm router-diagnostics collect` subcommand. For `mode: local` deployments, it:

1. Reads the installed `router-diagnostics` release's values (`namespace`, and `selector`/`configMapName` on the raw-manifest tier) to find the router's Service the same way the chart itself does — reusing the `router-diagnostics.routerServiceName` lookup already used to resolve the in-cluster Service DNS name for `mode: job` (see [`mode: job`](#mode-job) below).
2. Starts `kubectl port-forward svc/<resolved-service> 9090:9090` in the background and waits for the forwarded port to accept connections.
3. Runs `kubectl support-bundle --load-cluster-specs`.
4. Tears down the port-forward on exit (success, failure, or interrupt), so nothing is left running afterward.

`helm router-diagnostics collect` is the recommended invocation for `mode: local` — see [Invocation for `mode: local`](#invocation-for-mode-local) below. The manual `kubectl port-forward` + `kubectl support-bundle --load-cluster-specs` sequence remains documented as a fallback for customers who can't or don't want to install a Helm plugin (for example, a restricted CI runner where plugin installation isn't permitted):

```bash
kubectl port-forward svc/<router-service> 9090:9090   # in a separate terminal, left running
kubectl support-bundle --load-cluster-specs
```

**Why a Helm plugin over a standalone script:**

- It's discovered and versioned the same way the chart is — through Helm — rather than introducing a second, unrelated distribution mechanism (a script the customer has to separately trust, download, and keep up to date).
- It can read the release's own values directly via the Helm SDK, so it stays correct across chart upgrades to `router-diagnostics.routerServiceName`'s resolution logic without the customer maintaining a second copy of that logic in a shell script.
- It fits the "one small one-time install, then routine collection" shape the tool already uses for the `support-bundle` plugin, rather than adding a differently-shaped step to the customer's workflow.

**Rejected alternative: a standalone shell script distributed alongside the chart** (e.g. checked into the chart's GitHub repo, downloaded independently of Helm). Rejected because it duplicates the Service-resolution logic already expressed once in the chart's Helm templates, has no natural update or versioning story tied to the chart release the customer installed, and adds a second, differently-shaped installation step next to the existing Helm plugin (`support-bundle`) pattern rather than fitting it.

**Permissions:** `kubectl port-forward` requires `create` on the `pods/portforward` subresource in the router's namespace (port-forwarding to a Service resolves to one of its pods under the hood) — whether the customer runs the manual `kubectl port-forward` command or the plugin runs it on their behalf. See [Permissions for `mode: local`](#permissions-for-mode-local) below.

### Invocation for `mode: local`

**Official Apollo Helm chart:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace <namespace> \
  --set namespace=<router_namespace> \
  --set mode=local

helm router-diagnostics collect
```

**Raw-manifest / custom deployment:**

```bash
helm install router-diagnostics apollo/router-diagnostics \
  --namespace <namespace> \
  --set namespace=<router_namespace> \
  --set selector="app=my-router" \
  --set configMapName=my-config \
  --set mode=local

helm router-diagnostics collect
```

### Permissions for `mode: local`

Requires permission to create a ConfigMap in the target namespace, plus `create` on the `pods/portforward` subresource in the router's namespace to reach `router-metrics` — see [Reaching `router-metrics` under `mode: local`](#reaching-router-metrics-under-mode-local) above. Declining the latter does not fail collection; it only means `router-metrics` comes back empty rather than populated. Running the collection uses the invoking user's existing kubectl credentials.

### Cluster footprint for `mode: local`

Spec ConfigMap + Helm release metadata. Once installed, subsequent collections are just `kubectl support-bundle --load-cluster-specs`, with no reinstall. Customers who want nothing left behind can `helm uninstall` after collecting.

## `mode: job`

For teams whose kubectl access to production is restricted and who need a platform team to run collection on their behalf.

### Prerequisite: the collection binary for `mode: job`

The binary ships in **the Job's container image**, which Apollo owns and publishes.

**Apollo controls the troubleshoot.sh support-bundle version** in this mode, pinned by the image tag. This is the reproducible path, prefer it when a test needs a known-good collection. See [troubleshoot.sh support-bundle version](#troubleshootsh-support-bundle-version).

The image also needs `aws-cli` and `gcloud` bundled alongside the support-bundle binary — object storage uploads by invoking these CLIs directly, see `specs/storage/object_storage.md` .

### Chart values specific to `mode: job`

| Value | Required | Default | Purpose |
| --- | --- | --- | --- |
| `job.podAnnotations` | No | `{sidecar.istio.io/inject: "false", linkerd.io/inject: disabled}` | Annotations merged onto the Job's pod template, customer values win over the defaults — see [Service mesh environments](#service-mesh-environments) below |
| `job.podLabels` | No | `{}` | Arbitrary labels merged onto the Job's pod template |

```yaml
# templates/job.yaml — only rendered if mode: job
{{- if eq .Values.mode "job" }}
apiVersion: batch/v1
kind: Job
...
{{- end }}
```

### Invocation for `mode: job`

A platform team member with cluster access installs the chart with `mode=job` (plus `selector`/`configMapName` if the deployment is raw-manifest). The Job runs the collection using its namespace-scoped ServiceAccount and the platform team retrieves the bundle. See `specs/storage` for details on retrieving the bundle.

### Service mesh environments

**Injecting a sidecar risks the Job never completing.** A Job's pod is expected to terminate when its work finishes and Kubernetes only marks a Job `Complete` once every container in its pod has exited. An injected mesh proxy (e.g. `istio-proxy`) is a long-running sidecar that keeps waiting for traffic after the collection container is done, so the pod sits in `Running` indefinitely instead of reaching `Completed`. That leaves a stuck workload in the customer's production namespace and no clean signal that collection succeeded.

Given that, the chart sets `job.podAnnotations` to disable injection by default, but only for two meshes: Istio and Linkerd. This is a best-effort default, not a claim to cover every mesh, and it is a starting point the customer can override.

- **A different mesh** — the customer adds their mesh's own opt-out annotation via `job.podAnnotations`. Helm merges customer-supplied keys over the chart's defaults, so this is additive.
- **Policy requires every pod to stay in the mesh** — the customer overrides the specific default key back, e.g.:

  ```yaml
  job:
    podAnnotations:
      sidecar.istio.io/inject: "true"
  ```

  This is the customer's call, not our chart's. It's only safe from the stuck-`Completed` risk on a Kubernetes-native sidecar (`restartPolicy: Always`, GA in Kubernetes 1.29+, supported by recent Istio/Linkerd).

- `meta.json`'s `sidecar_injection_disabled` field records whether the chart disabled injection (`specs/collection/meta_json.md` → Render-time facts), ruling out one cause of an empty metrics section — but disambiguating a mesh-blocked scrape from a misconfigured exporter still needs the collected `router.yaml` (see `specs/collection/base_spec.md` → Service mesh and proxy environments).

- Disabling injection still leaves the Prometheus scrape itself blocked by a mesh enforcing strict mTLS — see [Running outside the mesh doesn't have to mean losing metrics](#running-outside-the-mesh-doesnt-have-to-mean-losing-metrics) for how to recover it.

### Permissions for `mode: job`

Additionally requires creating a Job, a namespace-scoped ServiceAccount, a Role/RoleBinding, and a ClusterRole/ClusterRoleBinding (for `nodeMetrics`'s cluster-scoped grants). Running the collection uses **a namespace-scoped ServiceAccount created by the chart**, run on the customer's behalf by a platform team member via the Job.

#### `nodeMetrics` RBAC

`nodeMetrics` needs three separate grants to reach `/api/v1/nodes/<node>/proxy/stats/summary`:

- **`nodes` (list)** — to resolve node names when neither `nodeNames` nor `selector` is set.
- **`nodes/proxy` (get)** — required unconditionally by the API server for any request matching the `/nodes/{name}/proxy/{path}` URL pattern. This is a broad grant: Kubernetes' own RBAC good-practices documentation states it "provides access to privileged kubelet APIs that can retrieve container logs or execute and attach to pod processes... bypasses audit logging and admission control," and is explicitly "not a read-only permission." What this tool does with it is read-only, but the grant itself authorizes more than that one use, and it cannot be scoped to just the router's nodes.
- **`nodes/stats` (get)** — required separately by the kubelet's own authorization check, layered on top of `nodes/proxy`, not a substitute for it.

Declining `nodes/proxy`/`nodes/stats` still leaves `nodes` access (node pressure conditions) and everything `clusterResources` provides — OOM kill occurrences and last state, restart counts, configured limits. What's lost is container memory/CPU trajectory over time — but `nodeMetrics` is a fallback for that signal, not the preferred path: enabling the Prometheus exporter gets the same container-level usage-over-time signal without any of these grants, so customers should be pointed toward Prometheus first. See `specs/collection/base_spec.md` → `nodeMetrics` is a fallback, not the preferred path.

See `specs/collection/base_spec.md` for the rest of the permission set the collectors need.

### Cluster footprint for `mode: job`

Spec ConfigMap + Helm release metadata + ServiceAccount/Role/RoleBinding. The Job itself is transient. Once installed, subsequent collections are just `kubectl support-bundle --load-cluster-specs`, with no reinstall; customers who want nothing left behind can `helm uninstall` after collecting.

## Running outside the mesh doesn't have to mean losing metrics

This applies to both modes — neither `mode: local` (the customer's own machine) nor an un-injected `mode: job` Job pod is inside the mesh. `logs`, `clusterResources`, `nodeMetrics`, `configMap` all reach their data through the Kubernetes API server or the kubelet, which the mesh does not sit in front of, so running outside it doesn't affect them. The Prometheus scrape is the one collector that talks directly to a router port, and a mesh enforcing strict mTLS will reject it from a pod outside the mesh, so the metrics port needs an explicit exception.

The fix is on the router's side: the customer exempts its metrics port from mTLS — Istio's `PeerAuthentication: PERMISSIVE` scoped to that port (or `traffic.sidecar.istio.io/excludeInboundPorts`), Linkerd's `config.linkerd.io/skip-inbound-ports`. This is platform-team guidance to apply once, not a chart setting.

If a platform team won't grant that then retrieving metrics will not be possible in v1. The only in-mesh alternative is an `exec`-based scrape from inside the router's own pod and `exec` collectors are deliberately excluded from the base spec and v1.
