# v1

What v1 of the Router Support Tool is, and what it deliberately is not.

v1 delivers **one spec, collected on demand, stored wherever the customer runs it.** Kubernetes only. Scheduled and threshold-triggered collection are v2 (`specs/trigger/`); additional specs are later milestones.

Detail lives with the layer it belongs to:

| Area | Spec |
| --- | --- |
| What is collected, and how it is sanitized | `specs/collection/base_spec.md` |
| Collector naming | `specs/collection/collector_naming.md` |
| Bundle self-description | `specs/collection/meta_json.md` |
| Chart, tiers, RBAC, execution location | `specs/deployment/v1/v1.md` |
| Apollo Operator specifics | `specs/deployment/v1/operator.md` |
| Customer-facing flows | `specs/user_experience.md` — **only the sections listed below** |

### Which parts of `user_experience.md` are v1

`specs/user_experience.md` documents both milestones in one file, because it is written as a customer would read it rather than split by version. Only the first two top-level sections are v1:

| Section | Milestone |
| --- | --- |
| The full lifecycle at a glance | Both — the diagram labels its v1 and v2 branches inline |
| **On-demand (flare-style) collection** | **v1** |
| ├ Which path applies to you | v1 |
| ├ Setup, step one: install the collection plugin | v1 |
| ├ Setup, step two: one chart, two modes | v1 |
| ├ Apollo Operator customers | v1 |
| └ Restricted-access clusters (`mode: job`) | v1 |
| **What you get, whichever path you used** | **v1** |
| ├ Support tool output | v1 |
| ├ Metrics require the Prometheus endpoint to be enabled | v1 |
| ├ Redaction preferences | v1 |
| ├ Cluster footprint | v1 |
| ├ Permissions for on-demand collection | v1 |
| └ Sharing with support | v1 |
| **Scheduled and threshold-triggered collection (v2)** and everything under it | **v2 — not v1** |

So: everything from *On-demand (flare-style) collection* through *What you get, whichever path you used* is the v1 experience. The v2 section describes a chart that does not exist yet, including a CronJob, a watcher Deployment, and object-storage push — **none of which v1 ships.**

Note that **there are two permissions sections**, deliberately named apart: *Permissions for on-demand collection* is v1's, and *Permissions for scheduled and threshold-triggered collection* is v2's. They are not the same list, and the v2 one is not yet settled — that chart has not been through the parameter-passing and deployment-tier analysis that produced `specs/deployment/v1/v1.md`, so nothing in it should be treated as decided.

## Use of troubleshoot.sh

The tool is built on [troubleshoot.sh](https://troubleshoot.sh), an open-source Kubernetes diagnostics project maintained by Replicated. **We do not build collection, packaging, or redaction machinery.** What we author is a SupportBundle spec — a YAML declaration of which of their collectors to run, against which targets, with which redactors — plus the Helm chart that delivers it and the Job image that can run it.

Useful entry points into their documentation:

| For | Link |
| --- | --- |
| Project overview | https://troubleshoot.sh |
| Installing the `support-bundle` plugin | https://troubleshoot.sh/docs/#installation |
| Collecting a bundle, and spec sources | https://troubleshoot.sh/docs/support-bundle/collecting/ |
| Discovering specs already in the cluster | https://troubleshoot.sh/docs/support-bundle/discover-cluster-specs/ |
| Collector reference — validate every field against this | https://troubleshoot.sh/docs/collect/ |
| Redactor reference | https://troubleshoot.sh/docs/redact/ |
| Analyzer reference (**not used in v1**, see below) | https://troubleshoot.sh/docs/analyze/ |

A SupportBundle spec has three parts. v1 uses two of them:

| Part | v1 | What it does |
| --- | --- | --- |
| **Collectors** | **Used** | Gather data — pods, logs, config, kubelet metrics, HTTP endpoints |
| **Redactors** | **Used** | Strip sensitive values after collection, before packaging. Their built-ins plus Apollo's custom rules |
| **Analyzers** | **Not used** | Evaluate collected data and emit pass/warn/fail findings |

Where the engine's behavior is load-bearing for a decision in these specs, the relevant source or documentation is cited at the point of the claim rather than summarized here — see for example `specs/collection/base_spec.md` → Why the Summary API and not cAdvisor's metrics endpoint. Validate any field against the collector reference above rather than assuming it exists; more than one field named in early design material turned out not to exist at all.

### Analyzers are out of scope for v1

troubleshoot.sh supports [analyzers](https://troubleshoot.sh/docs/analyze/): declarative rules that read what the collectors gathered and emit a pass, warn, or fail result. A `clusterResource` analyzer could, for instance, read the collected pod JSON and state outright *"router pod X was OOM-killed, 4 restarts"* rather than leaving support to find `lastState.terminated.reason` themselves.

**v1 ships no analyzers.** This is a deliberate scope decision, not an oversight.

The reasoning:

- **v1's job is to get the routine data into support's hands, not to diagnose.** The ticket analysis behind `specs/collection/base_spec.md` found the highest-leverage problem to be that support spends the first two or three rounds of every ticket asking for version, graph ref, and full config. Collecting those reliably solves that. Pre-judging what the data means is a different, later problem.
- **Analyzers are a second body of authored content with its own review burden.** Each one encodes a diagnostic opinion — what counts as too many restarts, which log line indicates a real fault — and a wrong or stale opinion is worse than none, because it tells a support engineer something confident and incorrect. That warrants its own review cycle rather than riding along with v1.
- **The collection surface is not settled yet.** Several open questions remain in `specs/collection/base_spec.md`, including the Operator's metrics port and PSI availability. Analyzers written against a moving collection surface will need rewriting.
- **Nothing about deferring them is costly.** Analyzers read data that is already in the bundle. Adding them later requires no change to what is collected, no new permissions, and no change to the chart — so there is no compounding cost to waiting, and no rework created by it.

**What this means in practice:** a v1 bundle is raw material. It answers "what was the state of this router" completely and answers "what is wrong with this router" not at all — that judgement stays with the support engineer reading it.

**When analyzers are proposed**, the strongest first candidates are the ones where the bundle already contains the answer but stating it explicitly saves a reader work:

- OOM kills — from Kubernetes events plus pod status `lastState.terminated.reason`
- Restart counts above a threshold
- Container memory approaching its configured limit
- Prometheus exporter not enabled, explaining an empty metrics section

That last one overlaps with the `expected_absences` mechanism in `specs/collection/meta_json.md`, which is worth noting: some of the explainability analyzers would provide is already being handled by having the chart record what it expected to be absent. A future analyzer proposal should say why an analyzer is the better mechanism for a given case, rather than assuming it is.
